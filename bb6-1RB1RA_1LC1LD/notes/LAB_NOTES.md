## 30 October 2026: setup and first look

Set up on the shared tools (`../../tools`): `lean/Machine.lean` generated by `bbtools.leangen` (namespace `BB6c`),
bounded runs in `lean/Blank.lean`, the reference simulator wrapped in `py/blank.py`.

The table, with the halting transition E0:

| state | on 0 | on 1 |
|---|---|---|
| A | 1RB | 1RA |
| B | 1LC | 1LD |
| C | 1LD | 0LB |
| D | 1RE | 0RF |
| E | halt | 1RD |
| F | 1RA | 1RB |

**Where a halt comes from.** E is entered only by D0 (write 1, move right), so the machine halts exactly when D reads
a 0 whose right neighbour is 0 (`halt_shape`, kernel). A sweeps right over 1s (A1 = 1RA) and turns at the first 0.

**Bounded runs.** No halt in 20,000 steps (kernel), 10⁷ (`native_decide`), 10¹⁰ (C `tmrun`, 5,580 ones, 6,278
cells visited), 10¹¹ (C, 12,410 ones, about 9 minutes).

**No linear invariant.** `bbtools.invariants` finds no conserved a·ones + b·pos + W[state] modulo 2 to 12.

**First records** (`python3 py/blank.py records 100000 60`): the head reaches new cells mostly on the right, as
`1^a 0 1^b A>0` and then `1^a 0 1^(b+1) B>0` one step later (steps 46, 155, 183, 444, 855, 1408, 1600, 2311, 3234,
...). The left part of the tape becomes a run of `1^2 0` blocks with an occasional `1 0`; D reaches the left end on a
0 or a 1, and in the first 3·10⁹ steps the cell to its right is always a 1 (655 times `D>0 1^2`, 193 times
`D>0 1 0`, 534 times `D>1`).

**Growth.** After t steps the width w is roughly √(t/250): t/w² is 207 at w = 5,080 (5.3·10⁹ steps) and 254 at
w = 6,277 (10¹⁰), so a little worse than quadratic time per cell, so a pass over the tape is likely the unit of the macro structure.

**Next.** Find the macro configuration (candidates: `1^a 0 1^b A>0` at the right end; D at the left end), the map
from one to the next as a function of the block lengths, and check it against direct simulation before stating it in
Lean.

## 31 October 2026: the pass structure

**The macro configuration.** Every time A reads the blank cell right of the visited tape, the tape is blocks of ones
separated by single 0s, `1^{b_1} 0 1^{b_2} 0 … 0 1^{b_k} A>0`: all 1,786 such moments in the first 10¹⁰ steps
(`tools/c/tmrun … at A R`, then `py/macro.py check-file`), with 2 to 8 blocks and no block shorter than 2. Each is a
new cell, so these *pass starts* are where the width grows. Three steps later the machine is in
`K = … 1^c 0 1^n B> 1 0 1 0^∞` with `n + 1 = b_k` (`start`).

**One pass.** B converts the last block from the right: `111 B> 1 0` becomes `B> 1 0 101`, 7 steps per three cells
(`TM.cross_l`). At the left end of the block the residue of `n` mod 3 decides:

* `n = 3m` (last block 3m + 1): the separator and the block to the left absorb 6 cells, and the converted words come
  back as a new last block. `n = 0` halts: D reads `0 0` at the right end (`K_zero_halts`; this is the right-end halt
  that the left-end thread's tape language allows).
* `n = 3m + 1` (last block 3m + 2): a carry crosses the block to the left (C with `010`, 9 steps per cell); the two
  blocks to the left gain 2 each, and the last block is rebuilt from the converted words.
* `n = 3m + 2` (last block a multiple of 3): the converter goes on into the next block (below).

On the way back to the right the head alternates between two phases one converted word `011` at a time: A before a
word, and Y (`0 0 1 B>`) before a word. From Y to A the head bounces to the block two to the left, and the two blocks
there gain 2 and 4 (`a_two`, `y_two`; iterated in `aphase`, `yphase`). Put together, with `x` the block left of the
last and `d` the one before it (0 if missing):

| last block | next pass start | Lean |
|---|---|---|
| 1 | halts | `K_zero_halts` |
| 4 | `… x+6, 1` (halts next) | `kA0` |
| 6t + 10 | `… x+2t+8, 4t+5` | `kA` |
| 6t + 7 | `… x+2t+6, 4t+3` | `kB` |
| 6t + 2 | `… d+2t+2, x+4t+3` | `kC` |
| 6t + 5 | `… d+2t+4, x+4t+5` | `kD` |
| 3m | recursive | open |

`next` in `lean/Macro.lean` is this table and `next_sound` proves that the machine follows it (kernel only, every
block length, every tape further left). `blank_passes` uses it from blank tape: `2 2 → 2 5 → 4 7 → 10 3`, and the
fourth is recursive. `py/macro.py` is the same map; it agrees with all 1,205 non-recursive passes to 10¹⁰ steps and
with direct runs from random block lists (`tests/test_machine.py`).

**Halting, as far as the map goes.** A pass start halts iff, following the map, a last block 1 appears; a last block 4
or the ending `1 0 1^2` lead there. The covered cases give last blocks `4t+5`, `4t+3`, `x+4t+3`, `x+4t+5` with
`x ≥ 2` in every pass start seen, so they never produce 1 or 4 themselves as long as all blocks stay ≥ 2; the
recursive case is where a small last block could come from.

**The recursive case (last block 3m + 3).** `K(3m + 2)` converts the block and stops at its left end in a second
mode, `1^c B> 0 0 1 …` (B reading `0 0`), with the converted words to the right. In that mode the next block is
converted too (`111 B> 0 0` becomes `B> 0 0 110`), and at its left end: residue 1 carries on into the next block in
the same mode, residue 2 turns back with E, residue 0 turns back with C (a bounce). The symbolic runs
(`tools/py/bbtools/symtm.py`):

```
L 0 1^c 0 (111)^j 1 1 B> 1 0 1 V  ->  L 0 1^c B> 0 0 (101)^j 1 0 1 1 V        (first block, n = 3j+2)
L 0 1^c 0 (111)^j 1 B> 0 0 1 V    ->  L 0 1^c B> 0 0 (101)^j 1 0 1 V          (mode 0, n = 3j+1: carry on)
L 0 1^c 0 (111)^j 1 1 B> 0 0 1 V  ->  L 0 1^c 1 1 1 E> (101)^j 1 0 1 V        (mode 0, n = 3j+2: turn)
L 0 1^c 0 (111)^j B> 0 0 1 V      ->  L 0 1^c C> 0 1 (011)^j 0 1 V            (mode 0, n = 3j: turn)
```

So the route depends on how many blocks to the left of the last are 1 mod 3: the list of routes is infinite, and
only a parametrised treatment will cover it (the lesson from the first machine). In the first 10¹⁰ steps the
converter crossed 0, 1, 2, 3 extra blocks in 400, 178, 3, 1 of the 581 recursive passes. On the way back the words
are a mix of `011` and `01`, and a `01` makes A start another converter run to the left (`L 0 1^x 0 1^y A> 0 1 0 1`
→ `… 1^y B> 0 0 1 1`), so the way back is recursive as well.

**Next.** The pass map for the recursive case: state the two converter modes and the A/Y phases on general word lists
(`011`, `01`) in Lean, as `Macro.lean` does for the covered case, and look for the quantity that keeps blocks ≥ 2.
## 31 October 2026: the left end, and halting only at the right edge

**The left end is one step deep.** D is entered by `E1 = 1RD` (so the cell to D's left is a 1) or by `B1 = 1LD`,
`C0 = 1LD` (so the cell to D's right is the 1 just written). Hence D with a 0 on its left, and so D at the left end,
always has a 1 on its right (`d_one_right`, `d_left_end`, kernel). The 1,382 left-end visits counted in the long run
are this, not a property of the run.

**A closed tape language.** `tools/py/bbtools/ctl.py` grows windows of K cells (letters 0, 1, `#` = blank from
here on) on each side of the head and abstract configurations (state, left window, right window) from the blank
start until nothing new appears. With K = 3: 12 left windows, 10 right windows, 245 abstract configurations, and
the only halting ones are E reading 0 with `111` on its left and `###` on its right. With K = 2 halts in the
middle of the tape are not excluded; K = 4 gives the same answer as K = 3 with 666 configurations. The right
automaton has no window with `00` past its first cell except in `#`, so past the head cell the written tape has no
`0 0`; the left automaton allows any word.

The same set as Lean data (`lean/EdgeCert.lean`) is checked by `decide +kernel` against the generic closure test of
`tools/lean/TM/CTL.lean`, whose soundness is proved there once for any machine. So, kernel only: every configuration
of the run from blank tape is covered (`reach_inv`); past the head two 0s in a row occur only in the blank region
(`right_no_double_zero`); `D>0 0` only with blank tape from D on (`d_zero_zero`); and the machine halts iff at some
step it is in E with blank tape from the head on (`halts_iff_edge`).

**What a halt would look like.** (Reasoning on the table, not in Lean.) A D entered from the right with blank tape
from D on came from `D>0 1` one step earlier, two cells to the left; following that back, the last D entered by a
left move (from B1 or C0) landed on a 0 with `1 (0 1)^k` and then blank tape to its right, k ≥ 0. So a halt needs a
left move to drop D two cells or more from the right edge onto `0 1 0 1 ... 0 1 |blank`. In the first 3·10⁷ steps
every left entry of D followed by at least one `0 1` pair stops on a 1 inside the tape; the closest to the edge was
2 cells, at step 5 (Python, not in the tests).

**Next.** The right edge is now the only place to watch: describe the configurations in which a left-moving B or C
reaches the last few cells, as part of the macro structure, and show that the tape there never ends in `0 1 0 1`
under a landing D.

## 31 October 2026: do blocks ever shrink below 2?

A pass start is *good* if every block is at least 2 and the last block is neither 1 nor 4 (1 halts on this pass,
`K_zero_halts`; 4 on the next, `kA0`).  The question is whether a good invariant holds for the whole run.

**Proved in Lean** (`lean/Blocks.lean`, kernel only): every covered pass keeps a pass start good (`next_good`), and so
does any run of covered passes (`nextIter_good`, with `nextIter_sound` tying it to the machine).  On a covered pass the
last block `b` either shrinks, `b + 5` becoming exactly `2(b + 5)/3` (`b ≡ 1 mod 3`: the output `2m - 1` is odd, so
never 4, and it is 1 only from 4), or becomes at least the block to its left plus 3 (`b ≡ 2 mod 3`) (`next_shrink`).
So from a good pass start, a halt needs a recursive pass (last block a multiple of 3) that breaks goodness.

**Computed** (`py/blocks.py`, a fast loop checked against the reference simulator):

* `run` on `tmrun … 10^11 at A R` output: all 3,845 pass starts in the first 10¹¹ steps are good.  Blocks shorter than 10
  are only first blocks (2, 4, 6, 8; the first block is always even) and last blocks of the first dozen passes; after
  pass 156 (about 6·10⁶ steps) the last block is always at least 22, and a last block 6 never occurs.
* `offsets`: a recursive pass from `…, x, 3j` ends with last block `2j + c`, where `c` depends on the blocks to the
  left but not on `j`; `c ≥ -1`, `c = -1` exactly when `x = 2`, and `c` is never 1 or 4 (3,000 random contexts).  For
  `x ≡ 0, 4, 5 (mod 6)` it is local: `(2x + 6)/3`, `(2x + 7)/3`, `(2x - 4)/3` plus what the blocks further left add
  for the first two; for `x ≡ 1, 2, 3 (mod 6)` the converter goes on and `c` is often 0.
* `exhaustive`, `random`: every good list whose next pass start is not good has last block 3 or 6 (all lists of up to 3
  blocks of 2..30 and up to 5 blocks of 2..12; 20,000 random lists with blocks up to 200 and last block not 3 or 6
  stay good).  Examples: `2 3 → 8 1`, `5 3 → 8 4`, `3 6 → 2 7 4`, `8 6 → 2 11 4`.  A last block 3 with a block of 6
  or more to its left was always safe, and a covered pass makes a last block 3 only as `…, x, 7 → …, x + 6, 3`.

**Why there is no finite invariant (heuristic).** The dangerous pass starts are last block 6 with offset 0 (→ 4 → 1),
and `…, 2, 3` or `…, 5, 3`.  A last block 6 comes from 9 with offset 0, 9 from 15 or 16, and so on: each shrinking pass
takes the last block to about two thirds, so the pass starts that can reach a halt are chains of residues of any
length, not cut out by a condition on a bounded number of blocks.  Whether the run halts is whether such a chain lines
up.  In the run the last block stays large: after the first 300 pass starts the fraction with last block below ε times
the width is 0.33, 0.047, 0.0085, 0.0006 for ε = 0.5, 0.2, 0.1, 0.05, and the smallest ratio is 0.036 (`298 1119 53`).
That falls faster than ε, so if it continues the expected number of last blocks of 9 or less over the whole run is
finite: evidence, not proof, that it never halts.

**Small blocks at the left end.** New blocks appear when the converter reaches the left end: the tape there becomes a
ladder `2 11 10 30 90 270 810 …` (each block three times the last from 30 on; e.g. `734 2409` → `2 11 10 30 90 270
1128 1606` at step 1.23·10⁹), which the following passes absorb from the right.  After pass 35 its leading 2 is the only block
below 10 (passes 370, 885 to 891 and 2,392 to 2,396 in the first 10¹¹ steps), and it is never the last block.

**Next.** With the recursive pass map in Lean (the other open item), `next_good` extends to all passes with last block
other than 3 and 6, and what is left is the arithmetic of the shrinking chains.

## 31 October 2026: the recursive pass in Lean

**Proved in Lean** (`lean/Recur.lean`, kernel only).  When the last block is `3j + 3`, `k_start` takes the pass
configuration to `L 0 1^c B> 0 0 1 0 1 1 (0 1 1)^j 0^∞`: the converter is now in front of the words `0`, `0 1` and
`j + 1` words `0 1 1`.  From there the pass is followed by a machine on

  `enc ⟨q, h, L, W⟩  =  … 0 1^{L_1} 0 1^{L_0} q> 1^h 0 1^{W_0} 0 1^{W_1} … 0^∞`

(blocks of length 0 allowed on the left, words `0 1^k` with `k ≥ 0` on the right).  Its steps, `astep`, are the rules
found earlier (the 31 October entry on the pass structure), with the converter at a block `n = 3j + r` before a word
`0 1^k` in `bstep`:

| state, head | what it reads | next |
|---|---|---|
| A, `1^h` | | A after the block, which gains `h` |
| A | `0 1^(k+1)` | B, with blocks `1`, `0`×k pushed |
| A | blank | the pass start, `K` |
| D | `0 1`, `0 1 1`, `0 1^(k+3)` | the block gains 2: D; F (with a block 0); B (with `1`, `0`×k) |
| E, `1` | `0 1`, `0 1 1`, `0 1^(k+3)` | the same with 3 |
| D, E | blank | halt |
| F | `0 1^k`; blank | A, the block gains `k + 1`; the pass start |
| C after `1^(c+1)` | `0 1`, `0 1^k` | the block moves into the word after (`s_c_move`, by induction); else B with `1`, `0`×k, `c` |
| C after `0` | `0 1`, `0 1^(k+2)` | the block before gains 2: F; B |
| B, `n = 3j + 1` | `0 1^k` | B one block further left, words `0`, `0 1`, `(0 1 1)`×j, the last `k` longer |
| B, `n = 3j + 2` | `0 1^k` | E with the block to the left `+3` |
| B, `n = 3j` | `0` | C, words `0 1`, `(0 1 1)`×j |
| B, `n = 3j + 3` | `0 1^(k+1)` | A, the two blocks to the left `+2` each |
| B, `n = 0` | `0 1^(k+1)` | C, the word one longer |
| B after `1 0 1^y 0 1^x` | blank | the pass start, `K` (`y_end`) |

Each line is a theorem `s_…` from the 19 new rules of `lean/Rules.lean`, and `astep_sound` puts them together; `arun`
iterates `astep` with fuel, `pass` is `next` or `arun` from `k_start`, and `pass_sound`, `passes_sound` say that
whatever they return (a next pass start, or a halt) the machine does.  Nothing says `arun` always finishes: where it
meets a case it does not cover (A reading `0 0`, E with more than one 1 under the head, …) it returns `none`.

**Computed.** Run by Lean (`#eval`, 5 s) from `1^10 0 1^3`, `passes` gives all 1,782 later pass starts of the first
10¹⁰ steps exactly; its Python transcription `next_full` gives all 1,786 (581 recursive, `py/macro.py check-full`, 6 s),
and agrees with direct runs from 300 random block lists with a last block that is a multiple of 3 (a test).  The kernel
evaluates 100 passes in about 10 s (`blank_passes_104`, to step 2,065,482) and 400 in about 2.5 minutes, so the
kernel-checked floor stays at 100 passes; with `native_decide` the whole 10¹⁰ steps would be a few seconds.

**What this gives and what not.** The pass map is now proved for every pass, but in the recursive case only as an
algorithm.  The block-length thread's offsets (`2j + c`, `py/blocks.py offsets`) are the closed form to aim for: a
recursive pass from `…, x, 3j` ends with last block `2j + c`, `c` local for `x ≡ 0, 4, 5 (mod 6)`.  Proving that from
`astep` means following the converter through the blocks to the left, by induction on `j` for the words `0 1 1` it
leaves behind.

## 31 October 2026: does the recursive pass always finish?

**Proved in Lean** (`lean/Finish.lean`, kernel only).  The block machine has a quantity that goes down at every step.
Take the cells from the head to the right end of the tape (the ones under the head, then the words `0 1^k`) and read
them from the right end: `key`.  Order such lists like a dictionary, with a 1 before a 0 and a list before its
extensions (`Below`).  Every step of `astep` that does not end the pass makes `key` smaller (`astep_key`): either the
head moves right past the ones under it and the next word (A, D, E, F, the C and B steps that leave with a `B` or `F`),
so `key` loses cells at its end, or the first word that changes, counting from the right end, gets longer (C moving a
block into the word after `0 1`, and every converter step of `bstep`), so a 0 of `key` becomes a 1 with nothing before
it changed.  In particular the block machine never comes back to a configuration.

That is not yet termination: dictionary order on lists of any length has infinite descending chains (`0`, `10`,
`110`, …), which here would be the head drifting left for ever.  It is termination as soon as the length of `key`
is bounded.  `arun_finishes`: if every configuration the block machine reaches has its head within `N` cells of the
right end and is a case `astep` covers, then `arun` ends the pass (next pass start or halt) within `3^N` steps;
`pass_finishes` is the same for `pass` from `K ls n`.  (The proof sends `key` to a number below `3^N`, `val`, which
the order makes strictly decreasing, `val_mono`.)

**What is open.** Two hypotheses remain, and neither has a short proof that I can see.
* *No uncovered case.* From a tape with a block 0 or 1 the block machine can get stuck (e.g. `ls = [1]`, `j = 0`
  ends in B on a block 1 with a block 8 to its left and no words to its right).  From good tapes it never did; ruling it out needs facts about the
  last word and the blocks next to the head when the words run out.
* *No drift to the left.* The head goes left only as the converter, through blocks 1 mod 3 and one block more, and
  it turns at the left end of the tape, but each visit there can leave the tape one cell longer
  (a C step moves the leftmost block into the words and F starts a block 2 one cell further left).  Bounding the
  number of such visits is the real content.  Linear potentials (cells plus nonnegative multiples of counts of words
  and blocks by value and residue) do not work: a linear program over 500 kinds of step from random runs is
  infeasible.

**Computed** (`py/macro.py reach`, `test_key_goes_down`; `key` is checked at every step).  Over 1,000 random good
contexts (0 to 8 blocks of 2 to 40) with `j` from 0 to 40, every recursive pass finishes, and how far left of the
original tape the head gets depends only on the blocks, never on `j` (at most 8 cells there; 14 in a wider search).
So the words `0 1 1` of the last block are handled without touching the left end, as `2j + c` with `c` independent of
`j` suggests.  On the run itself (`tmrun … 10^10 at A R`, then `py/macro.py reach`, 14 minutes): the 582 recursive passes in
the first 10¹⁰ steps all finish, `key` going down at every step, in at most 11,419 steps of the block machine, and
the head gets at most 6 cells past the left end of the tape (in 559 of them at most 1 cell).

## 31 October 2026: the last block after a recursive pass, `2j + c`, in Lean

`lean/Formula.lean`, kernel only.  From `K ls (3j - 1)` the block machine starts at B before the words `0`, `0 1` and
`j` words `0 1 1`.  Following the run over many lists shows two things.  First, the words `0 1 1` that `k_start` leaves
are never touched until the machine comes back to them, and it always does so at A after an `F` step (`F` reading a
word, the block gains the word plus 1), with only words `0 1 1` ahead.  Second, from there it is one loop:

| from | to |
|---|---|
| A, blocks `a, b`, words `0 1 1`, `0 1 1`, … | A, blocks `a + 4, b + 2` (`tail_two`: A token, B at 1, B at 0, C, the block `a` swept into the next word, C after 0, F) |
| A, blocks `a, b`, no words | the pass start, last block `a` |
| A, blocks `a, b`, one word `0 1 1` | the pass start, last block `a + 2`, `b + 2` left of it (`y_end`) |

so from A before `a` with `m` words left the last block is `a + 2m` (`tail_end`, every `a`, `m`, tape to the left).

The machine only reads the words in front of it: one step of `astep` is the same whatever follows the first two words
(the first one, except for C before `0 1`), `astep_app`, by cases.  So `pre` runs the block machine once from `0, 0 1`,
taking words `0 1 1` from an unbounded supply when there are too few (`u` counts them), and stops at A with only words
`0 1 1` ahead (`p` of them), returning the blocks `a, b, M`.  `pre_sound`: for every supply of `u + m` words the real run
gets to A before `a` with `p + m` words.  With `tail_end`, `recur_sound`: for every `j ≥ u` the next pass start has the
blocks `b + 2⌈(p + j - u)/2⌉, M` and last block `a + 2(p + j - u) = 2j + c`, `c = a + 2p - 2u`.  In the 7,000 lists tried,
`u ≤ 2`, and for `u = 2` the formula also holds at `j = 1` (`p = 0` there).

**x = 2, closed form.** B at 2 before `0` gives E with one 1, which reads `0 1` (D, block `+3` twice), D reads `0 1 1`
(F), F reads `0 1 1` (A with block 3), then the loop with `j - 2` words: last block `2j - 1`, the block left of the 2
gains `8 + 2⌈(j-2)/2⌉` (`recur_two`).  So `…, d, 2, 3` reaches `…, d + 8, 1`, which halts (`recur_two_three_halts`), and
for `j ≥ 2` the new last block is odd and at least 3, so a good pass start stays good (`recur_two_good`).

**Small lists.** `recur_small`: on all 819 lists of 1 to 3 blocks of 2 to 10 the kernel runs `pre` (and for `u = 2` the
pass map at `j = 1`) and finds `c ≥ -1`, `-1` exactly for `x = 2` (`decide +kernel`, 35 s).  The Python mirror
`macro.pre` agrees with `next_full` on random lists (`test_formula`).

**What is not proved** (as of this section; for every list see "c ≥ -1 for every list of blocks" below). That `c ≥ -1` for every list: before the loop the converter can carry on through any number of
blocks that are 1 mod 3, and `pre` follows it only list by list.  Observed: for `x = 6r + 5` the offset is `4r + 2` for
every list tried; for `x ≡ 0, 1 (mod 3)`, and for some `x = 6r + 2` such as 14 and 32, it depends on the blocks
further left.
That `pre` always stops is not proved either (the same question as for `arun`).


## 31 October 2026: the pass map with step counts, to 10¹²

**Why counts.** `passes_sound` gives `Reaches init (K ls n)`, which bounds the run in passes but says nothing about
the step at which the pass start comes.  Every rule in `lean/Rules.lean` already states its exact length, so
`lean/Count.lean` carries the lengths along: `nextC`, `astepC`, `arunC`, `passC`, `passesC` are the maps of
`Macro.lean` and `Recur.lean` case for case, each returning the exact number of machine steps beside its outcome, and
`passesC_sound` (kernel only) says the machine gets there in exactly that many.  The two-word phases cost
`aph t y` (`10y + 18` per double word, `y` growing by 4); a sweep of a block of `c` into the next word costs `9c`.
The counted copy does not have to agree with the uncounted one for anything proved here; it does, on every pass run.

**The run.** `blank_passesC`: blank tape to `K [10] 2` in 186 steps (the pass start `1^10 0 1^3 A>0` at step 183).
`blank_reaches_1e12`: then 8,257 passes, 2,654 of them recursive, evaluated by `native_decide` in about 2.5 minutes,
reach the pass start `1^11866 0 1^17246 A>0` at step 1,000,110,302,407.  So `blank_runs_1e12`: no halt in the first
10¹² steps, trusting the compiler for that one evaluation and the kernel for everything else (`Axioms.lean`).
`blank_runs_1e10`, `blank_runs_1e11` follow.  The 10¹⁰ range alone is 1,784 passes (5 s), 10¹¹ is 3,842 (13 s).

**Cross-check.** The pass starts from `passC`, step numbers and blocks, agree exactly with all 3,843 pass starts of
`tools/c/tmrun … 1.001·10¹¹ at A R` from step 183 on (8 minutes of C), so the step counts are right as well as proved.

**What this gives.** A Lean-checked floor of 10¹² steps, ten times the C simulation, in a few minutes; the floor is
cheap to raise (the cost per pass grows with the tape width, about √(t/250)).  It is still only a floor.

## 1 November 2026: bounding the drift to the left

The aim was a proof that from a good start the head of a recursive pass gets at most a few cells past the left end of
the tape, which with `astep_key` (`lean/Finish.lean`) would make every pass finish.  Not done; what was found:

**A bound on the drift is the whole problem.**  Every step moves the cells right of the head towards the left end
(`astep_key` in cell terms: whole words are consumed, or a word's separator moves left).  Any measure built from the
words alone, a multiset of separator positions or a dictionary order with longer words first, needs a bound on how far
left things go to be well founded, so a bound on the drift is equivalent to termination, not a step towards it.
The tape grows only when the converter runs off the left end, after every block left of the head has been turned into
words; then a C step moves the leftmost block into the words and F starts a block 2 one cell further left.

**No constant bound.**  The 582 recursive passes of the first 10¹⁰ steps go at most 6 cells past the left end, but
over all good lists the drift grows with the number of blocks: a hill climb (`j = 1`) finds 6 with 4 blocks, 9 with 8,
11 with 12 and 13 with 24 (`[25, 14, 14, 7, 7, 25, 8, 29, 5, 4, 28, 5, 14, 10, 3, 16, 11, 5, 2, 10, 21, 4, 11, 19]`).
So a theorem would have to bound the drift by something like the number of blocks, and that needs the structure of
the pass.

**`pre` (`lean/Formula.lean`) reaches arbitrarily deep.**  How many blocks of the original list `pre` touches is not
set by the first block that stops the converter (a block not 1 mod 3): over 20,000 random lists of 1 to 8 blocks,
lists whose first block already stops it are still dug into to depth 8.  The way back sweeps right, two words `0 1 1`
at a time, over blocks `x, y`, and every word `0 1` or `0 1 1 1` on the way converts `y` back into words, sometimes
`x` and further blocks too, so the left part is rebuilt many times (11 times for `[7, 10, 40, 25, 21]`).  An
induction over the blocks, as for `c ≥ -1`, has to follow these rebuilds.

Linear potentials (cells plus nonnegative multiples of counts of words and blocks by value and residue) were ruled
out before; the same holds with counts of the run of blocks 1 mod 3 next to the head.  The next idea to try is a
description of the A states of `pre`: the blocks left of the head (up to 8 in the samples), and the words, which
beyond the first two are always 1, 2 or 3 (5,000 random lists, every A state), and a measure on the sequence of irregular words `1` and `3` between the runs of
`0 1 1`.

## 1 November 2026: `c ≥ -1` for every list of blocks, in Lean

`lean/Offset.lean`, `lean/OffsetData.lean` (kernel only).  For every list `ls` of blocks of at least 2, of any length,
if `pre` stops then it returns `a, b, M`, `p`, `u` with `2u ≤ a + 2p + 1`, and `2u ≤ a + 2p` unless `ls` starts with 2;
`u ≤ 2`; `b ≥ 2` and `M` is blocks of at least 2 then 0s (`offset_bound`).  With `recur_sound`, for every `j ≥ 2` the
pass from a good list with last block `3j` reaches a list of blocks of at least 2 with last block `2j + c ≥ 2j - 1`
(`recur_next`).  Everything is conditional on `pre` stopping, which is the open drift question above.

**How.**  Instead of an induction over the blocks, an abstract interpretation of the block machine.  A number is a code:
exactly 0 to 3, or "at least 4" with its residue mod 3 (`gD`).  The blocks to the left keep three codes and, for the
rest, one of "all 0", "a block of at least 2, then blocks of at least 2, then 0s", "anything" (`gL`).  The words keep
two codes, and the rest is empty or a run of words 1, 2, 3 in which every 1 is followed by a 2, given by its first and
last word (`Seq`, `gW`): the notes above saw that beyond the first two the words are always 1, 2 or 3.  `u` is kept
exactly, with a flag for "the block left of the last is 2".  Each concrete step of `pre` is matched by an abstract one
(`absAstep_sound`, `absNext_sound`), where a step that cannot be described gives `none`.  From the 11 starts (block 2;
3 to 6 by code; or none; with "blocks of at least 2" or "all 0" behind) 4,463 descriptions are reachable; none is
`none`, `u ≤ 2` throughout, and at every one where `pre` may stop (A, no ones under the head, words possibly all 2) the
bound holds with `p ≥` the number of explicit words and the first block at least its code's least value.

**Getting the kernel through.**  Computing the closure inside `decide +kernel` ran out of 16 GB.  So `OffsetGen.lean`
evaluates the closure (`reach`, about 9 s in the interpreter), sorts it by an injective key and writes it as a balanced
search tree, split into 64 named subtrees of about 70 descriptions; `OffsetData.lean` has one `decide +kernel` per
subtree that each of its descriptions is fine (`okA`: bound where it may stop, every abstract step lands in the tree and
keeps the flag), and `check_ok` joins them (127 checks, about 70 s, 1.3 GB).  Membership is only ever used in the
direction "found in the tree, so in its list" (`TS.mem_toList`), so a wrong tree could only fail the check.  `check.sh`
regenerates the file and compares.

**What was needed.**  A first version lost precision: for a code "at least 4, residue 1" the number of words `0 1 1`
in the B step was allowed to be 0, which let `u` grow without bound.  Restricting it per code (`jsA`) fixed that; the
first-block bound also had to allow 0s after the blocks of at least 2 (`gzB`, `tailB`).


## 1 November 2026: `pre` never gets stuck

**Question.**  Can the abstraction of `lean/Offset.lean` show that `pre` always stops from a good list (blocks of at
least 2)?

**Acyclicity fails.**  Dumping the 4,463 reachable descriptions and their abstract steps: the graph has two strongly
connected parts of 1,838 descriptions each, so there is no simple proof that the abstract run is finite.  This is
expected from the drift question: a description forgets how far left the head is, and the conversion of a word and its
consumption undo each other in the description.  `u` stays at most 2 throughout (0: 2,191 descriptions, 1: 2,182,
2: 90).

**What does follow** (`lean/Stops.lean`, kernel only).  At every description the block machine has a next step unless
`pre` stops or takes a supply word there (`progA`; `prog_ok` checks it with `decide +kernel` on the tree in a few
seconds, `progA_sound` transfers it to every described configuration).  So the run of `pre` from a good list never
meets a case the block machine does not cover; the hypothesis "meets no case it does not cover" of `Finish.lean` is
gone.  The measure `(3 − u) · 3^N + val N (key c)` goes down at every step of `pre`: an ordinary step lowers the key
(`astep_key`, `val_mono`), and taking a supply word raises `u` by one, which pays for any change of the key since
`val N _ < 3^N`.  Hence if every configuration of the run keeps at most `N` cells (head offset plus cells of the words),
`pre` stops within `4 · 3^N` steps (`pre_stops`), and `recur_next` holds with that bound in place of "if `pre` stops"
(`recur_next_bounded`).

**Still open.**  The bound itself: that the head does not drift left without bound.  It is now the only gap between
the kernel results and "every recursive pass from a good list finishes, with last block at least `2j − 1`".

## 1 November 2026: a ranking function for `pre`? What the A states show

**Aim.**  A measure that goes down along `pre` from every good list, so that `pre` stops with no assumption
(`pre_stops` needs only a bound on the cells).  Not found; what was found narrows the question.

**Two words at a time** (`py/tokens.py check`, 3,000 random good lists, no exception; `test_tokens`).  Look at `pre`
only at A with no ones under the head.  Between two such states it eats exactly the first two words.  Call a word
other than 2 *irregular*.  Only the pair `1 2` writes new words: the converter runs left through the blocks that are
1 mod 3 (each becomes a word 1 followed by 2s), stops at the first block that is not, and A comes back; what it
writes ends in a word 3 where the 2 was (rarely, nothing).  So the irregular word in front moves exactly one word to
the right and every new irregular word is to its left.  The other pairs write nothing: `2 2` is the loop of
`tail_two` (blocks `a, b` gain 4 and 2), `2 1` and `2 3` remove the irregular word, `3 2` removes the 3 and pushes a
new block 4, `3 1` and `3 3` are rare.  In closed form, with the blocks `a_1, …, a_k` (nearest first) 1 mod 3,
`a_i = 3 j_i + 1`, then a block `b`, then `c, d`:

| `b` | blocks after | words written in place of `1 2` |
|---|---|---|
| `3m`, `m ≥ 1` | `c + 3, d + 2, …` | `2^{m-1} 1 2^{j_k} 1 … 1 2^{j_1} 3` |
| none (all blocks 1 mod 3) | `2, 2` | `2^{j_k} 1 2^{j_{k-1}} 1 … 1 2^{j_1} 3` |
| `3m + 2` | `3, c + 6, …` (roughly; small cases differ) | `… 2^{m-2} 3` |

**Tokens.**  Count irregular words plus nonzero blocks.  Over the same lists this count never goes up, except by
exactly 1 on a step where the tape grows at the left end (`+2` or `+6` added to a block past the leftmost one starts
a new block).  Growth steps are few (at most 4 in random lists of up to 10 blocks; a hill climb, `py/tokens.py climb`,
finds about one per block: 5 with 2 blocks, 9 with 8, 12 with 12), and they can come one after another: from `[4, 3,
19]` three in a row while one word 1 walks right through the 2s, the count going 3, 4, 5.

**No count works.**  The row "none" above shows why no potential linear in counts of words and blocks (weights by
kind, any residue) can go down: with weight `β` per block, `α₁`, `α₃` per word 1 and 3, it changes by
`(k - 2)(α₁ - β) + α₃`, which is `α₃ > 0` for `k = 2`; and `k = 0, 1` with the row `3m` force `α₁ ≤ β`.  An LP over
1,357 kinds of step from random runs (counts by position, kind and residue; and again with a free constant for each
of 1,736 abstract states: the first two blocks, the last two, the first two words) is infeasible, both for "cells +
potential does not grow" and for the weaker "potential drops on every growth step".

**Orders that fail.**  Dictionary order on the tokens read from the right end is what `astep_key` already gives at
word level, and has the same infinite chains (`1`, `3 1`, `3 3 1`, …: new irregular words on the left).  Multisets of
token positions (Dershowitz–Manna), measured from the right end or from the current left end, blocks by either end,
words by any of their cells, every ranking of the kinds: 2 to 13 % of steps go up, always at the growth steps or right
after them.  Dictionary order on the tokens read from the left: at least 108 of 498 kinds of step go up.  The position
of the head at successive growth steps does not move monotonically either.

**What a proof needs.**  Termination is equivalent to finitely many growth steps (between them the cells are bounded
and `pre_stops` applies).  Growth needs every block between the head and the left end to be 1 mod 3 (or the carry to
end one or two blocks from it), and leaves fresh blocks `2, 2`, `3, 2`, `3, 6`.  A proof will have to use what the
fresh blocks and the words written with them look like, for example that from the fresh blocks the next carry
cannot reach the left end until a word of the stream to the right has been used up; the reduction to two words per A
state above is the place to start.
