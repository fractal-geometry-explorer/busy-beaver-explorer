# 1RB1LE_1RC1LF_0RD1RD_1LE0RE_0LA0LB_---1LE

bbchallenge id 99198. One of the six-state holdouts whose halting from blank tape is open.  It is a
**base-4 counter feeding a stack of timers**.  The left part of the tape is a base-4 counter whose digits are the
words `10`, `1`, `101`, `11` (0 to 3), separated by runs of pairs `110`; every visit of the head to the left end adds
one.  Only when the counter overflows does the head sweep all the way to the right end, through a list of long
blocks of ones that behave like timers: at every such visit the last block loses 9 ones, the one before it 24, the
one before that 96, then about 384.  Its twin is [`1RB1LF_0RC1RC_1LD0RD_0LE0LA_1RA0LB_---1LD`](../1RB1LF_0RC1RC_1LD0RD_0LE0LA_1RA0LB_---1LD/README.md), which runs the same counter and
the same timers (all blocks but the last are equal at every right-end visit, the last differs by 186 (606 vs 420 at the first such visit)).

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 1LE |
| B | 1RC | 1LF |
| C | 0RD | 1RD |
| D | 1LE | 0RE |
| E | 0LA | 0LB |
| F | --- | 1LE |

## What it does

### The counter (left end)

At each visit of the left end in state E, the tape is `E>0 (110)^n0 d0 (110)^n1 d1 ... (110)^nk dk` followed by
the timer blocks, where each digit `d` is one of `10` (0), `1` (1), `101` (2), `11` (3).  One round, from a visit of
the left end to the next, adds one to the counter (`lean/Rules.lean`, generated by `py/rules.py`, for all run
lengths and any tape `R` to the right):

| round start | next round start | rule |
|---|---|---|
| `(110)^n 10 (110)^m R` | `(110)^(n+1) 1 (110)^m R` | `inc0` |
| `(110)^n 1 (110)^m R` | `(110)^(n+1) 101 (110)^(m-1) R` | `inc1` |
| `(110)^n 101 (110)^m R` | `(110)^(n+1) 11 (110)^m R` | `inc2` |
| `(110)^n 11 (110)^m d R` | `(110)^(n+1) 10 (110)^m (d+1) R` for `d` = 0, 1, 2 | `carry0`, `carry1`, `carry2` |

So the first run of pairs grows by one cell triple per round (the "sqrt" side: a round takes a sweep across the
growing left part), and a carry out of digit `i` happens once every `4^(i+1)` rounds.

### The timers (right end)

When the carry runs off the last digit, the head sweeps on to the right end, turning pairs `110` into `111` on the
way, and the tape seen there is a list of blocks of ones.  At successive right-end visits (C simulation, `E` at
the right end):

The last block loses 9 at each visit, the one before it 24, the one before that 96 (for example 664, 571, 475,
379, 283 and 3187, 3091, ..., 2707), the next about 384; the blocks on the left are the counter, written out.  The
right end is reached only at overflows, which come exponentially rarely, so the right side of the tape grows like
the logarithm of the step count (the "exp" side of the triage).  When a timer runs out it is refilled from the
blocks on its left (as 378 becomes 489 at step 2,019,687); how exactly is not yet written down.

### How it could halt

The halting transition is F0, and the only way to it is the **E-chain**: with the head in state E on the last 1 of
a run of c ones, `E1 -> 0LB`, `B1 -> 1LF`, `F1 -> 1LE` turn each `111` (read from the right) into `110` in 3 steps.
When the run is used up, what follows depends on c mod 3 (`lean/Chain.lean`, generated by `py/chain.py`, for all k
and any tape on both sides):

| run | end of the chain | rule |
|---|---|---|
| c = 3k+3 | E on the 0 before the run, then `E0 -> 0LA` | `chain0` |
| c = 3k+4 | B on that 0, then `B0 -> 1RC` | `chain1` |
| c = 3k+5 | F on that 0: **halt** | `chain2` |

So the machine halts exactly if E ever starts a chain on a run of length 2 mod 3 (c = 2 halts at once).  In the
simulated run (to 2·10^10 steps) every chain starts on a run of length 0 or 1 mod 3: the left part of the tape is
in "1-form" (blocks of ones separated by single 0s, the far blocks 1 mod 3), the right part in "P-form" (runs of
`110` with short digit units `1^a 0`, a ≤ 6).

### The right-end map (second pass)

Write a right-end visit as the head in state **D on the last cell** of `1^b0 0 1^b1 0 ... 0 1^b(m-1)` (this is one
step from the E-visit of the table above; the last block is one more: 382 here for 381 there).  `c/rmap.c` runs
the machine from such a tape to the next visit of the same kind.  For lists in which no block is used up, the map
is (computed: `py/gencheck.py` on 60 random lists with m ≤ 5, blocks 1 mod 3, all as predicted; also 15 lists on the twin)

    (b0, ..., b(m-1))  ->  (6·4^m + 4, b0 - d(m-1), ..., b(m-2) - d1, b(m-1) - d0),   d0 = 9, d(i) = 6·4^i (i ≥ 1)

that is, the counter writes a new block 6·4^m+4 at the left and every timer j places from the right loses d(j).
When a block is smaller than its decrement the result is piecewise linear in it with period 12, with merging of
neighbouring blocks; for example, from `3001 v 901 1201` (m = 4):

| v | next visit |
|---|---|
| 4 | 376, 2911, 880, 1192 |
| 7 | 484, 2884, 874, 1192 |
| 10 | 556, 2866, 871, 1192 |
| 16 | 556, 2863, 880, 1192 |
| ≥ 97 | 1540, 2617, v−96, 877, 1192 (generic) |

and v ≡ 1 mod 12 merges blocks.  A new block 6·4^m+4 is left with 4 after the next visit (see 1540, 4 and 24580, 4 in
the table) and is then used up.  Tiny lists (`4`, `7 7`, `10 10`) never come back to the right end: the machine
becomes a bouncer from them.  Continuing the real run from the D form of the visit at 8,352,788,565
(`98308 38692 2620 3613 22087 2707 1042 382`), the next right-end visit comes 26,203,435,131 steps later with
`223972 42316 24694 2080 21703 2611 1018 373` (computed, `c/rmap.c`; so no halt to about 3.46·10^10 steps).

### What did not work

Closed-tape-language (CTL) searches over the counter tokens (runs of `110`, digit units, blocks taken modulo
small numbers, a DFA for the far tape) all failed: the abstraction loses whether a block is larger than its
decrement, and then admits small "worlds" in which a timer is tiny and the D zigzag eats a big block into a chain
of `10`, which reaches a run of length 2 mod 3.  Making the classes exact blows up the state count.  Non-halting
seems to rest on numeric relations between the blocks (that the timers are always refilled before they meet the
bad residue), not on a regular pattern.  The CTL search with K ≤ 6 also failed (first pass).

## Status

Open.  Lean (kernel): the six counter rounds in `lean/Rules.lean` for all run lengths; the E-chain and its three
endings in `lean/Chain.lean` for all k; `lean/Blank.lean`: the halting configurations (`step_none_iff`), no halt in
10,000 steps by the kernel, in 10,000,000 by `native_decide`.  The twin halts from blank tape iff this machine
halts from blank tape started in state B (kernel, `twin` in the twin's `lean/Twin.lean`).  Computed: the right-end
table, the generic right-end map and its exhaustion examples.  C (`tools/c/triage.c`): no halt in 1,000,000,000
steps; C (`c/runs.c`, direct simulation): no halt in 2·10^10 steps; `c/rmap.c`: no halt to about 3.46·10^10.

## For later

- Close the right-end map: write the exhaustion cases (period 12 in the small block, with merges) as a finite table
  of linear pieces, prove each piece with `symtm`/`seqtm` rules (the D zigzag through a small block, the sweep that
  writes 6·4^m+4), and then find an invariant on block lists (residues mod 3 and 12, and a size order such as
  "each block is at least its decrement or is one of the known small shapes") that excludes a chain on a run 2 mod 3.
- The invariant has to be numeric (see "What did not work"); a CTL with counter classes is unlikely to suffice.
- The twin halts exactly when this machine, started in state B, halts (proved). That is not this machine's run from
  blank tape, so the two holdouts are two questions; the same method should serve both.
- `holdouts/1RB1LE_0RC---_1RD0LA_1RE0RB_0LA0LF_0LD1LF` has the same kind of structure (blocks shrinking by 4,
  12, 48, 192 per round) and may share the analysis; not looked at in the second pass.

## Long accelerated run (16 November 2026)

**No halt in the first 5.71·10^90 steps from blank tape, and none in the first 3.10·10^89 steps from blank tape
started in state B** (the twin's question). Both bounds are trusted (Python), and they are bounded runs.

The model is the one asked for under "For later": one counter round at a time, with the right-end phase included.
`py/digits.py` reads the tape at every left-end visit (state E on the blank cell at the left end, one sample per
round). It reads it **mirrored**, so that the generic window engine of
`holdouts/1RB0LF_1LC0RC_1RA1LD_0RB0LE_1LC0LB_---1LA/py/digits.py` (class `Spec`) can be reused unchanged on the
mirror machine `1LB1RE_1LC1RF_0LD1LD_1RE0LE_0RA0RB_---1RE`. In the mirror the tape is a list of digits
`(110)^r W`, with walls W0 = 1/1, W1 = 3/1, W2 = 3/1 1/1, W3 = 4/1 (blocks 1^a 0^b; these are the README's
digits 0 to 3), plus a few walls that appear briefly after overflows. Any other single block becomes a wall of its
own name. After the walls come the last run and the end cells `11` (or `1`). A round (a "sweep") is computed by a
**symbolic run of the machine** (`tools/py/bbtools/symtm.py`) on a window. The window holds the carry chain
(trailing W3) and the stop digit, more digits if the run needs them, and the whole tape at an overflow. In that
last case the symbolic run goes to the right end, through the timer phase, and back. Runs longer than 7 are
variables. Each rule is cached by its window shape, so no law is assumed. The "unusual event" at each left-end
visit, the zero-length runs left by an overflow (W2 W0 with r = 0, ends `1`), is just another window shape.
`py/accel.py` is a copy of that holdout's `py/macro4.py` (hierarchical macros Inc(k) derived symbolically on
window keys, plus cycle skips that are applied only while every run stays in its class). Two changes: the window
rule caches are capped for memory, and start state B is an option.

Validation:
- `python3 py/digits.py check FILE` against the direct C sampler `c/sampb.c` (`./sampb MACHINE A|B 400000000`):
  every one of the 19,219 rounds up to 4·10^8 steps (start A, 19 overflows) and of the 19,307 rounds (start B)
  is predicted exactly, both the tape and the step count, with 0 mismatches and 0 unparsed samples.
- `python3 py/accel.py test 100000 1000000 [B]`: the macros agree with plain sweeps, states and step counts, over
  10^6 rounds from step 10^5 (both starts).
- Runs: `python3 py/accel.py run 100000 2400 CKPT.pkl [B]`. Start A reached step
  5,710,760,547,545,706,450,531,585,424,618,529,375,013,306,891,261,050,110,631,683,661,118,727,156,559,638,200,078,015,117
  after 2.28·10^45 rounds, with 79 digits. Start B reached step
  309,912,429,635,717,488,255,026,042,251,054,316,912,233,544,920,575,434,371,030,188,155,071,676,538,482,240,087,883,083
  after 5.54·10^44 rounds, with 73 digits. Neither run stopped: no symbolic rule halted, needed a case split or
  failed to parse. A halt would show up as one of these, because the E-chain on a run of length 2 mod 3 needs a
  split on the residue of a variable run, or is met by a concrete run.
  End states: `/mnt/project-files/halt-hunt/f06left/` (pickles `(state, step, rounds)`).
- Progress slows with depth. From about 10^88 steps on, the step count grows only by a factor of about 15 per
  10 minutes, because new macros are derived all the time (31,005 in 150 s, with an uncapped cache). A likely
  cause is that the top runs (about 1.13·10^6, 3.2·10^5, 3.2·10^6, ...) are below the macro thresholds 4^(k+1),
  so they enter the keys as constants. These top runs shrink only by a few hundred between 10^43 and 10^90 steps, so their exhaustion,
  the next place where a halt could come from, is far beyond this run.

## Top-part forecast: the timers (21 November 2026, group C)

**Exact bound unchanged** (region-memo 8.56·10^262). **Forecast: the first right-end timer exhaustions after 5.71·10^90 steps (start A) do not
halt; 28389 overflow cycles followed** (trusted computation of a reduced model; the reduction is an argument checked on data).

- **Method** (`py/forecast.py`, code in `holdouts/1RB0LF_1LC0RC_1RA1LD_0RB0LE_1LC0LB_---1LA/py/forecast.py` and `cmacro.py`). The digit model counts at the bottom, and a carry reaches a digit only through carry walls, so the first P digits (the *top part*) see only carries arriving from below; the lower part decides only *when*. The top part is therefore followed alone: the top P digits of an exact state are kept, the rest is replaced by 3 zero digits with runs of 10^60 (the *reduced model*), and the reduced tape is run by `cmacro.py`, an exact macro engine over the same digits.py window rules (macro keys hold only walls, small runs and parities; every comparison on a big run is recorded as a linear condition and checked at each application). One overflow cycle of the top part is a translation of its runs while none is near exhaustion, so K cycles are jumped at once (top += K·D); near an exhaustion the cycles are run one by one. A merge at index j changes only digits j-1 and j, so the forecast of the top part holds until the real run at index P-1 (lifetime run/|D|) is used up. The forecast says nothing about step counts (they depend on the lower part) and assumes the lower part keeps delivering carries, which is what every exact run so far shows. 
- Check of the reduction (P = 40, start A, from 5.71·10^90): the 9 top events of a 200 s exact run agree with the reduced model.
- The timers are the top runs of the mirrored model: a cycle (a right-end visit) moves the runs at index 2, 4, 6, 8, ... by
  -3, -8, -32, -128, ... words of `110` (the README's 9, 24, 96, 384 cells). From the 16 November state (`py/accel.py`
  pickle, 5.71·10^90), with P = 40: the timers `1191614`/`1186943` (lifetime about 9,300 cycles) and `317959`/`317669` (about 40,000)
  are used up and refilled from their neighbours; 28389 cycles were followed in about 400 s (the cycles after a refill are run
  one by one and each derives new window macros, so this is slow), with no STOP: the E-chain on a run of length 2 mod 3,
  which would be the halt, never came up as a window rule.
- Next deciding event: the next timer exhaustion beyond cycle 28389 (the top runs then: see the forecast log); the run
  at index 2 (about 1.13·10^6, -3 per cycle) lasts about 3.5·10^5 cycles.

## The timer map and the first collapses (24 November 2026)

**No halt through the first two run-outs of the top timer, from blank tape and from state B** (3.3 million overflow
cycles after 5.71·10^90 and 3.10·10^89 steps; reduced-model forecast, so this is a forecast, not a bound on steps).

**The exact timer map.** One overflow cycle of the *full* exact state at 5.71·10^90 steps (no reduction, the
condition-macro engine `cmacro.py` on `py/accel.py`'s digit model; `python3 py/timermap.py exact`) shows the
tape at an overflow as `W0 W0 ([T1] W2 [0] W0) ([T2] W2 [0] W0) ... ([T75] W2 [0] W0)`: 75 timers, each a run of
`110` words. In one cycle, while none runs out, every one of the 75 timers moves by exactly

    T1 -> T1 - 3,   Tk -> Tk - 2·4^(k-1)  (k ≥ 2)

(9, 24, 96, 384, ... cells: the README's right-end map, now checked on all 75 timers of the real run). Their
lifetimes Tk / dec(k) at that point are 377,828 cycles for T1, 39,741 for T2, 99,526 for T3, and much less
deeper down (T75 runs out in the next cycle), so run-outs below the top happen all the time; they are the
counter itself. Only a run-out of T2 can change T1 (it then loses 2 instead of 3 once, which shifts T1's
residue mod 3); deeper run-outs change only the timer above them. `lean/TimerMap.lean` proves the arithmetic: K
cycles at once, a cycle keeps T1's residue mod 3, and when T1 runs out.

**What a run-out of the top timer does** (`python3 py/timermap.py runout MACHINE R CYCLES`, the saved state with T1
set to R words, then forecast):

| T1 at run-out | what happens | halt? |
|---|---|---|
| 0 mod 3 (3 → 0) | T1 is dropped, every timer moves up one level and loses 6·4^(k-1) − 2 words in that cycle | no |
| 1 mod 3 (4 → 1) | the top digit becomes `[1]W0`, is used up in the next cycle, then the same shift | no |
| 2 mod 3 (5 → 2) | `[1]W0 [0]W0` on top, then a carry through every digit (all W3) and a rebuild: T1 and T2 are both used up and the deeper timers are rewritten (the new T1 is about 2.33·10^9) | no |

So the halt (an E-chain on a run of length 2 mod 3, `lean/Chain.lean`) is not produced by any of the three
residues, at least in the contexts tried.

**The real runs** (forecast of the top 40 digits, `forecast.py run` then `py/timermap.py cont`, 2·10^6 + 1.3·10^6
cycles, about 3 hours on one core each):

| run | first T1 run-out | residue | second T1 run-out | residue | at cycle 3.3·10^6 |
|---|---|---|---|---|---|
| A (blank tape, from 5.71·10^90) | log cycle ≈ 378,209 | 0 | ≈ 1,107,000 | 0 | T1 = 16,587,577 (1 mod 3), T2 = 2,399,645,476 |
| B (state B, from 3.10·10^89) | ≈ 378,172 | 0 | ≈ 1,106,860 | 2 (T1 and T2 used up) | T1 = 2,331,944,982 (0 mod 3), T2 = 26,154,194,953 |

No window rule halted, split or failed to parse in either run (0 STOP). The runs pass about 15,000 smaller
timer events each. The next top event: A's T1 runs out with residue 1 after about 5.53·10^6 more cycles; B's in
about 7.8·10^8 cycles.

**How far the reduction is checked.** The forecast follows the top 40 digits with the lower part replaced by
three zero digits. Compared at the overflows (canonical snapshots, top 10 digits = timers T1 to T4;
`python3 py/timermap.py compare 1200 10`), a 1,200 s exact run and the reduced model agree on all 138 overflow
cycles the exact run reached (T1 from 1,133,495 to 1,133,081). The older check `forecast.py validate`, which
samples whenever the top two digits change, finds the two runs out of step from sample 106 on (1,442 of 1,743
samples, 1,800 s exact run): inside a cycle the two runs pass the top W0/W1 phases at different moments (for
example exact `[1133457]W0 [317852]W1` against reduced `[1133456]W1 [317852]W0`), so that check compares
different phases, not different results. The argument that the top part sees only carries arriving from below is
still an argument checked on data; the exact full state can be run only about one cycle per 10 to 20 s, far too
slow for 10^6 cycles, because run-outs deep in the counter happen at almost every cycle.
