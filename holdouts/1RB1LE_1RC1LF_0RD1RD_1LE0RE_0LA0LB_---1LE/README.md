# 1RB1LE_1RC1LF_0RD1RD_1LE0RE_0LA0LB_---1LE

bbchallenge id 99198. One of the six-state holdouts whose halting from blank tape is open.  It is a
**base-4 counter feeding a stack of timers**.  The left part of the tape is a base-4 counter whose digits are the
words `10`, `1`, `101`, `11` (0 to 3), separated by runs of pairs `110`; every visit of the head to the left end adds
one.  Only when the counter overflows does the head sweep all the way to the right end, through a list of long
blocks of ones that behave like timers: at every such visit the last block loses 9 ones, the one before it 24, the
one before that 96, then about 384.  Its twin is [`1RB1LF_0RC1RC_1LD0RD_0LE0LA_1RA0LB_---1LD`](../1RB1LF_0RC1RC_1LD0RD_0LE0LA_1RA0LB_---1LD/README.md), which runs the same counter and
the same timers (all blocks but the last are equal at every right-end visit, the last differs by 186 (606 vs 420 at the first such visit)).

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 1LE |
| B | 1RC | 1LF |
| C | 0RD | 1RD |
| D | 1LE | 0RE |
| E | 0LA | 0LB |
| F | --- | 1LE |

## What it does

### The counter (left end)

At each visit of the left end in state E, the tape is `E>0 (110)^n0 d0 (110)^n1 d1 ... (110)^nk dk` followed by
the timer blocks, where each digit `d` is one of `10` (0), `1` (1), `101` (2), `11` (3).  One round, from a visit of
the left end to the next, adds one to the counter (`lean/Rules.lean`, generated by `py/rules.py`, for all run
lengths and any tape `R` to the right):

| round start | next round start | rule |
|---|---|---|
| `(110)^n 10 (110)^m R` | `(110)^(n+1) 1 (110)^m R` | `inc0` |
| `(110)^n 1 (110)^m R` | `(110)^(n+1) 101 (110)^(m-1) R` | `inc1` |
| `(110)^n 101 (110)^m R` | `(110)^(n+1) 11 (110)^m R` | `inc2` |
| `(110)^n 11 (110)^m d R` | `(110)^(n+1) 10 (110)^m (d+1) R` for `d` = 0, 1, 2 | `carry0`, `carry1`, `carry2` |

So the first run of pairs grows by one cell triple per round (the "sqrt" side: a round takes a sweep across the
growing left part), and a carry out of digit `i` happens once every `4^(i+1)` rounds.

### The timers (right end)

When the carry runs off the last digit, the head sweeps on to the right end, turning pairs `110` into `111` on the
way, and the tape seen there is a list of blocks of ones.  At successive right-end visits (C simulation, `E` at
the right end):

The last block loses 9 at each visit, the one before it 24, the one before that 96 (for example 664, 571, 475,
379, 283 and 3187, 3091, ..., 2707), the next about 384; the blocks on the left are the counter, written out.  The
right end is reached only at overflows, which come exponentially rarely, so the right side of the tape grows like
the logarithm of the step count (the "exp" side of the triage).  When a timer runs out it is refilled from the
blocks on its left (as 378 becomes 489 at step 2,019,687); how exactly is not yet written down.

### How it could halt

The halting transition is F0, and the only way to it is the **E-chain**: with the head in state E on the last 1 of
a run of c ones, `E1 -> 0LB`, `B1 -> 1LF`, `F1 -> 1LE` turn each `111` (read from the right) into `110` in 3 steps.
When the run is used up, what follows depends on c mod 3 (`lean/Chain.lean`, generated by `py/chain.py`, for all k
and any tape on both sides):

| run | end of the chain | rule |
|---|---|---|
| c = 3k+3 | E on the 0 before the run, then `E0 -> 0LA` | `chain0` |
| c = 3k+4 | B on that 0, then `B0 -> 1RC` | `chain1` |
| c = 3k+5 | F on that 0: **halt** | `chain2` |

So the machine halts exactly if E ever starts a chain on a run of length 2 mod 3 (c = 2 halts at once).  In the
simulated run (to 2·10^10 steps) every chain starts on a run of length 0 or 1 mod 3: the left part of the tape is
in "1-form" (blocks of ones separated by single 0s, the far blocks 1 mod 3), the right part in "P-form" (runs of
`110` with short digit units `1^a 0`, a ≤ 6).

### The right-end map (second pass)

Write a right-end visit as the head in state **D on the last cell** of `1^b0 0 1^b1 0 ... 0 1^b(m-1)` (this is one
step from the E-visit of the table above; the last block is one more: 382 here for 381 there).  `c/rmap.c` runs
the machine from such a tape to the next visit of the same kind.  For lists in which no block is used up, the map
is (computed: `py/gencheck.py` on 60 random lists with m ≤ 5, blocks 1 mod 3, all as predicted; also 15 lists on the twin)

    (b0, ..., b(m-1))  ->  (6·4^m + 4, b0 - d(m-1), ..., b(m-2) - d1, b(m-1) - d0),   d0 = 9, d(i) = 6·4^i (i ≥ 1)

that is, the counter writes a new block 6·4^m+4 at the left and every timer j places from the right loses d(j).
When a block is smaller than its decrement the result is piecewise linear in it with period 12, with merging of
neighbouring blocks; for example, from `3001 v 901 1201` (m = 4):

| v | next visit |
|---|---|
| 4 | 376, 2911, 880, 1192 |
| 7 | 484, 2884, 874, 1192 |
| 10 | 556, 2866, 871, 1192 |
| 16 | 556, 2863, 880, 1192 |
| ≥ 97 | 1540, 2617, v−96, 877, 1192 (generic) |

and v ≡ 1 mod 12 merges blocks.  A new block 6·4^m+4 is left with 4 after the next visit (see 1540, 4 and 24580, 4 in
the table) and is then used up.  Tiny lists (`4`, `7 7`, `10 10`) never come back to the right end: the machine
becomes a bouncer from them.  Continuing the real run from the D form of the visit at 8,352,788,565
(`98308 38692 2620 3613 22087 2707 1042 382`), the next right-end visit comes 26,203,435,131 steps later with
`223972 42316 24694 2080 21703 2611 1018 373` (computed, `c/rmap.c`; so no halt to about 3.46·10^10 steps).

### What did not work

Closed-tape-language (CTL) searches over the counter tokens (runs of `110`, digit units, blocks taken modulo
small numbers, a DFA for the far tape) all failed: the abstraction loses whether a block is larger than its
decrement, and then admits small "worlds" in which a timer is tiny and the D zigzag eats a big block into a chain
of `10`, which reaches a run of length 2 mod 3.  Making the classes exact blows up the state count.  Non-halting
seems to rest on numeric relations between the blocks (that the timers are always refilled before they meet the
bad residue), not on a regular pattern.  The CTL search with K ≤ 6 also failed (first pass).

## Status

Open.  Lean (kernel): the six counter rounds in `lean/Rules.lean` for all run lengths; the E-chain and its three
endings in `lean/Chain.lean` for all k; `lean/Blank.lean`: the halting configurations (`step_none_iff`), no halt in
10,000 steps by the kernel, in 10,000,000 by `native_decide`.  The twin halts from blank tape iff this machine
halts from blank tape started in state B (kernel, `twin` in the twin's `lean/Twin.lean`).  Computed: the right-end
table, the generic right-end map and its exhaustion examples.  C (`tools/c/triage.c`): no halt in 1,000,000,000
steps; C (`c/runs.c`, direct simulation): no halt in 2·10^10 steps; `c/rmap.c`: no halt to about 3.46·10^10.

## For later

- Close the right-end map: write the exhaustion cases (period 12 in the small block, with merges) as a finite table
  of linear pieces, prove each piece with `symtm`/`seqtm` rules (the D zigzag through a small block, the sweep that
  writes 6·4^m+4), and then find an invariant on block lists (residues mod 3 and 12, and a size order such as
  "each block is at least its decrement or is one of the known small shapes") that excludes a chain on a run 2 mod 3.
- The invariant has to be numeric (see "What did not work"); a CTL with counter classes is unlikely to suffice.
- The twin halts exactly when this machine, started in state B, halts (proved). That is not this machine's run from
  blank tape, so the two holdouts are two questions; the same method should serve both.
- `holdouts/1RB1LE_0RC---_1RD0LA_1RE0RB_0LA0LF_0LD1LF` has the same kind of structure (blocks shrinking by 4,
  12, 48, 192 per round) and may share the analysis; not looked at in the second pass.

## Deep exact run

No halt in the first 1.99x10^19 steps: the macro simulator `holdouts/1RB0LB_1RC0LA_1LB0RD_1RE1RD_1RB1RF_1LA---/c/msim.c` with blocks of 6 cells ran
from blank tape to step 19,991,980,548,116,890,254. It is exact, and at this block size it agrees with the
direct simulator after 2,000,018,533 steps (`python3 holdouts/1RB0LB_1RC0LA_1LB0RD_1RE1RD_1RB1RF_1LA---/py/deep.py run 240`, then `verify`).
