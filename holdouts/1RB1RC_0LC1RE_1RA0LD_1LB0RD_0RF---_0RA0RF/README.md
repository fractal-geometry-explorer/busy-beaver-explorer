# 1RB1RC_0LC1RE_1RA0LD_1LB0RD_0RF---_0RA0RF

bbchallenge id 1965. One of the six-state holdouts whose halting from blank tape is open (group G07, family: **binary down-counter in the gaps (00 = 0, 000 = 1), nested reloads**).

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 1RC |
| B | 0LC | 1RE |
| C | 1RA | 0LD |
| D | 1LB | 0RD |
| E | 0RF | --- |
| F | 0RA | 0RF |

## What it does

**A binary counter written in the gaps, counting down, inside a list of blocks.** Stop the machine each time the
head, in state A, is at the right end of the tape. The tape is a list of blocks of 1s separated by gaps of two or
three 0s (rarely one). Read the gaps as digits, `00 = 0`, `000 = 1`, `0 = 2`, lowest digit at the right: they are a
counter, and **almost every visit of the right end decrements it by one**:

    gaps (as digits)   ... 1 1 0 0       (the lowest nonzero digit is the 1 in third place)
    becomes            ... 1 0 1 1       (it drops by one, the zeros below it become 1s)

and the blocks move with it: the block left of that digit gains 3 cells, the block right of it gains 3 (0 if the
digit was a 2), the blocks further right lose 1 each and the **last block loses 4**. If the digit was the lowest one,
only the block on its left changes (+3). An example from the run (step 2,791 to 3,005; blocks, then gaps):

    3 . 6 .. 8 .. 25 . 23 . 18      gaps 2 3 3 2 2  = digits 0 1 1 0 0
    3 . 6 .. 11 . 28 .. 22 .. 14    gaps 2 3 2 3 3  = digits 0 1 0 1 1

How a decrement happens: the head runs left from the right end; state D/B turns every block it crosses into the
sparse form `1 0 1 0 ...` (two cells per step) until it finds the first `000` gap; there it turns, and state A runs
back to the right end turning the sparse stretch into 1s again (Lean `fill_10`), with the gap and block lengths
shifted as above.

Checked against the run (the earlier pass): of the 36,789 consecutive visits of the right end up to 10^9 steps, **36,674 follow the
rule exactly** (`py/counter.py`). The 115 others are the interesting moments:

* **the last block is used up** (54 times): it loses 4 at every other decrement; when it would go negative the
  counter is cut short, a digit is removed or the last block restarts from the block before it;
* **the counter reaches zero** (12 times) or a section of it does (49 "other" cases): a new digit `2` (single 0 gap)
  is created further left, with a new block of 3, and all the digits below it become 1s: the counter is reloaded,
  longer than before.

The reloads nest. Block lengths further left are built up by these events; late in the run they include runs like
`15 31 63 127 255 511 1023 2047` (powers of two minus one), the trace of counters inside counters, and the blocks at
the far left stop changing for good ("freeze": the prefix up to `1^69` is fixed from step 4.5·10^5 on).

Halting would need state E to read a 1 (transition E1), which happens only in a configuration the ordinary decrement
never produces; it would have to come out of one of the rare reload events.

## One visit, exactly

Between two visits of the right end (state A on a new cell) the head makes **one leftward sweep and one rightward
refill**, never turning in between (`c/visits.c`: the refill never has C read a 1 or B read a 0 straight after A,
for all 36,752 visits up to 10^9 steps). Both passes are proved piece by piece in `lean/Rules.lean`, each piece for
every length (generated by `py/rules.py` with `bbtools.symtm.prove`):

* start (`p_start`): `L A> 0^inf` becomes `L C> 1 0^inf` (the last block is one longer, hence odd, for the sweep);
* the sweep takes the 1s two at a time (`11` becomes `01`), and at the left end of a block:
  * odd block behind `00`, block before nonempty (`p_pass`): `L 1 00 (11)^w C> 1 R` becomes `L C> 1 0 1 0 (01)^w R`, the sweep goes on;
  * odd block behind `000` (`p_stop_odd`): `L 000 (11)^w C> 1 R` becomes `L 1 A> 0 1 0 (01)^w R`;
  * even block behind at least one 0 (`p_stop_even`): `L 0 1 (11)^w C> 1 R` becomes `L 1 A> 0 1 (01)^w R`;
  * odd block behind a single 0 (`p_halt`): `L 1 0 (11)^w C> 1 R` reaches `L 1 E> 1 ...`, **the only halt of the sweep**;
* the refill, for segments of length at least 3: `p_fill_first` (`A> 0 1 0 0 1 (01)^w` becomes `1 1 0 0 (11)^w A> 1`),
  `p_fill_two` (`A> 1 0 1 0` becomes `1 1 1 1 A>`), `p_fill_mid` (`A> 0 1 0 1 0 1 (01)^v` becomes `1 1 0 0 0 (11)^v A> 1`),
  `p_fill_end` (`A> 1 0^inf` becomes `1 1 A> 0^inf`).

**The ordinary decrement, for any number of blocks** (`dec_general`, `lean/Decrement.lean`, by induction over the
list of blocks crossed): for any `L`, `a ≥ 1`, `m ≥ 3`, `b₁ ... bᵣ ≥ 3` (r ≥ 0),

    L 000 1^(2a+1) 00 1^(2b₁+1) ... 00 1^(2bᵣ+1) 00 1^(2m) A> 0^inf
    reaches
    L 111 00 1^(2a+4) 000 1^(2b₁) ... 000 1^(2bᵣ) 000 1^(2m-4) A> 0^inf

(the lowest digit 1 becomes 0, the 0s below it become 1s). With `dec_last` (the case where the last block itself is
behind `000`) it covers **36,604 of the 36,790 visits** up to 10^9 steps (`py/visits.py`). The other 186 are the
reloads: 114 sweeps stop at an even block, 48 stop at an odd block behind `000` with short blocks after it, 16 have the
last block too short, 8 reach the left end. None reaches the halting case.

## Status

Open. Proved in Lean (kernel): the halting configurations, 10^4 steps (10^7 native), the shift rules
(`lean/Shifts.lean`), every piece of a visit (`lean/Rules.lean`), and the ordinary decrement for any number of
blocks (`lean/Decrement.lean`). Trusted: no halt in 10^9 steps; every visit is one sweep and one refill; the counts
of visit kinds above.

What is missing is an **invariant**: a set of tapes at the right end that contains the start, is closed under every
kind of visit (the ordinary one and the reloads) and never puts an odd block behind a single 0 in the sweep's path.
In the run, the block after a single 0 is even when the next gap is `00` and odd when it is `000`; reading the tape
as tokens (block length, exact up to 8, otherwise parity; then the gap after it) the active part is almost all
"odd block, `00`" and "even block, `000`" tokens. But the sets of token pairs and token triples seen in the run are
**not** closed: running one visit (exactly, by direct simulation) on tapes built from them gives new pairs and
triples, and repeating this soon builds tapes that halt. Cell-level closed tape languages (bbtools.ctl windows up to
K = 6, windows with position parity anchored at the end, run-length windows with parity, with depth from the left
end) all allow a halt. So the invariant has to carry information over many blocks, through the nested reloads.

## Next steps

* Write the reload visits as rules, as `dec_general` was written: the stop at an even block (`p_stop_even` and the
  refill after it), short blocks (segments of length 0, 1, 2 shift the refill's alignment), the last block used up,
  the sweep reaching the left end.
* Find the invariant at the level of whole counters: the reloads nest counters inside counters, so the natural
  description is recursive (a counter whose digits are counters); check it with the exact visit map on many tapes
  before trying a proof.
* Then a proof by induction over visits in Lean, or a CTL whose left automaton is the invariant's automaton
  (`tools/lean/TM/CTL.lean` accepts any automata, not only windows).
