# 1RB1RE_1LC1LA_1RA0LD_1LC0LE_0LF0RA_---1RC

bbchallenge id 132695. One of the six-state holdouts whose halting from blank tape is open. (group G07).
Family: **counter that overflows at the left end**. Decision: **open**. Same table as 74982, mirrored.

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 1RE |
| B | 1LC | 1LA |
| C | 1RA | 0LD |
| D | 1LC | 0LE |
| E | 0LF | 0RA |
| F | --- | 1RC |

## What it does

This machine is the table of [`1RB0RD_1LC0RA_1LF1LD_0RE0LC_---1LB_1RB1RC`](../1RB0RD_1LC0RA_1LF1LD_0RE0LC_---1LB_1RB1RC/README.md) (74982) read in a mirror, with the states renamed: A, B, C,
D, E, F here are C, F, B, A, D, E there (`is_mirror`, Lean). So its run from blank tape is, cell for cell in the
mirror, the run of 74982 started on blank tape in state C, and everything proved there for every tape holds here.
The two machines start in different states, so they are two separate halting questions.

In this machine's own orientation the tape is

```
d 1 xk 1 ... 1 x2 1 x1 1 1 (01)^(n+1)        the head arrives from the right, on the first 1 left of the units
```

- **The units** `01` at the right end (runs of a single 1) are 74982's wall. The head crosses them twice per sweep
  and one unit is added at the blank end each time.
- **The counter** is the digits x1, x2, ..., xk on every second cell, with a 1 between neighbours, and a last cell d
  at the left end of the tape. Read as runs of 1s separated by single 0s this is a row of odd runs: a digit 0 ends a
  run. The rewrites seen in a run (`(1,3) -> 5`, `(3,3) -> 7`, ...) are the carry of 74982's automaton: three carry
  states a, b, c; a: 0 becomes 1 and the carry stops, 1 becomes 0 and it goes on in b; b: 0 becomes 1 (go on in a),
  1 becomes 0 (go on in c); c: 0 stays (c), 1 stays (a).

An **overflow** is a carry that runs through all the digits and reads the last cell d at the left end. What it does
then is proved in Lean for every counter (`lean/Ends.lean` in the folder of 74982):

| carry state at d | d = 0 | d = 1 |
|---|---|---|
| a | d becomes 1 | **extension**: the counter gains a digit |
| b | **the machine halts** | **conversion**: all the units become counter digits |
| c | **conversion** | **the machine halts** |

After every one of these the last cell is 1, so from the first overflow on the machine halts exactly when a carry
reaches the left end **in state c**. On the tape that is the head arriving on the leftmost 1 in state D with a 1
just crossed (`D1 -> 0LE`, `E0 -> 0LF`, `F0` halts): the head comes off the left end in state E instead of D, as
`halts_iff_edge` says.

## The run from blank tape

16 steps from blank tape the machine is at an arrival with one unit, the single digit 1 and last cell 1
(`twin_arrival`, kernel). From there on it is the event system of 74982:

- `twin_halts_iff_events` (Lean, kernel only): **the machine halts from blank tape if and only if the event system
  `evstep` halts from (wall of 1 pair, digits [1], last cell 1).**
- The overflows of the run are events of that system (`py/events.py twin` in the folder of 74982, which also
  compares the system with the machine on the first 200,000 steps):

  | sweep | step of the overflow | event | units before | digits after |
  |---|---|---|---|---|
  | 1 | 28 | conversion | 1 | 3 |
  | 3 | 91 | conversion | 2 | 6 |
  | 8 | 309 | extension | 5 | 7 |
  | 10 | 450 | conversion | 7 | 15 |
  | 21 | 1,252 | extension | 11 | 16 |
  | 53 | 7,545 | conversion | 43 | 60 |
  | 410,976 | 506,587,790,058 | conversion | 410,923 | 410,984 |

  (The overflow at step 3 is before the first arrival.) The steps are those found by `c/tok.c`; the sweeps and
  events are computed by the event system.
- `twin_conversion`, `twin_halts_iff_after` (Lean, with `native_decide` for the 410,975 sweeps): the 410,976th
  sweep is a conversion of 410,923 units, and the machine halts from blank tape if and only if the event system
  halts from the counter it leaves: 410,922 ones, a 0, the 60 marks of the last carry and a 1 (410,984 digits), last
  cell 1, one unit. So the machine does not halt in the first 5·10^11 steps, and the last conversion is why the
  tape changed from mostly units to a wide region of short runs.

## The left end: three outcomes

A carry that reaches the left end arrives in state C on the last cell of the leftmost run of 1s. It crosses the run
three cells at a time (`1 1 1 <C` becomes `<C 1 0 1`, 7 steps, whatever lies to the right), so the outcome depends
only on the length r of the part of the run it has to cross, mod 3:

    r = 3m      C reads the blank: C0 -> 1RA, the head bounces (the run grows by one cell)
    r = 3m+1    C1 -> 0LD, D reads the blank: D0 -> 1LC, C0 -> 1RA, the head bounces
    r = 3m+2    C1 -> 0LD, D1 -> 0LE, E0 -> 0LF, F reads a 0: **halt**

`lean/LeftEndHalt.lean` proves the third line for every m and every tape to the right (`halts_left2`, on
`left2` generated by `py/left_end.py`). In the run from blank tape the carry arrived with r = 6 four times, r = 4
twice and r = 1 once (`c/entries.c`, the entries of the head into the leftmost run in 3*10^10 steps, i.e. the
overflows up to step 7,545): never 2 mod 3 so far.

**It is not an invariant.** After the overflow at step 7,545 the tape at the next visit of the right end (step 8,130)
is, in run lengths,

    4 1 5 1^5 3 1^4 5 (1 3)^14 1

a prefix, a reservoir of 14 pairs `1 3` (made from the old units) and one unit. `py/overflow.py` starts the plain
machine from the same tape with k pairs instead of 14 and runs it to its overflow:

| k | visits to the overflow | steps | the head leaves in |
|---|---|---|---|
| 0 | 54 | 11,494 | C |
| 1 | 51 | 10,664 | C |
| 2 | 201 | 131,808 | C |
| 3 | 463 | 667,712 | C |
| 4 | 727 | 1,624,558 | C |
| 5 | 1,919 | 11,149,928 | C |
| 6 | 1,647 | 8,226,132 | C |
| 7 | 2,815 | 23,923,670 | C |
| 8 | 11,135 | 372,561,398 | **E: halts** |
| 9 | 13,609 | 556,344,400 | D |
| 10 | 44,247 | 5,875,764,342 | D |
| 11 | 66,857 | 13,413,161,642 | C |
| 12 | 83,241 | 20,791,657,350 | C |
| 14 | 410,921 | 506,590,247,458 | C (the machine's own run: the overflow near step 5.07*10^11) |

So with 8 pairs instead of 14 the machine would have halted at its next overflow. The number of visits to the overflow
grows roughly like 2^k but irregularly (it is not even monotone), and the prefix left by each overflow is different
every time. Chaining such experiments (take the tape after an overflow, shorten its reservoir to 0..7 pairs, run to
the next overflow; 44 runs over three generations) gave 4 halts, 15 exits in D and 14 in C (the rest ran out of
time). The outcome of an overflow behaves like a throw with three faces, one of which halts.

**The next overflow.** The overflow at step 506,587,790,058 left a reservoir of about 137,000 pairs (410,921 units,
3 units per pair), so the next overflow comes after roughly 2^137,000 visits, about 10^(8*10^4) steps. Its outcome
needs the exact prefix at that time; no shortcut is known.

## The carry after a conversion: a front in a periodic background

A dedicated pass looked for closed forms between overflows (an exact accelerator of the event system). There are
none of the usual kind; this is what the system looks like instead (`py/front.py`, plain computation).

- **Tokens.** Carry state b is "flip the digit, then go on as c", and c copies 0s up to the next 1. So one sweep
  reads the digits from the units' side as tokens: `0 -> 1` (the sweep ends), `1 0 -> 0 1`, `1 1 0^j 1 -> 0^(j+2) 1`.
- **Blocks of three.** Under carries in state a three digits are a wheel of 8 positions (000, 100, 011, 111, 001,
  101, 010, 110) that lets 3 carries of 8 through, as a, b and c. Carries b and c move the wheel by -1 and by
  "minus the position", each with a correction of 4 at positions 3 and 7, so the wheels do not add up to a number
  system: no weights on digits and carry states are conserved except a parity.
- **After the conversion.** The counter is 1^410,922 0 (60 marks) 1. The first sweep runs through all the ones
  and turns them into (001)^136,974. From then on the carries touch only a prefix, and everything behind the furthest
  carry is still 001 001 ...: a front that moves into a periodic background. After 2,000,000 sweeps it has reached
  digit 70 (3.8 digits per doubling of the number of sweeps so far), which puts the next overflow at the order of
  2^(1.1·10^5) sweeps.
- **Why it is slow.** The carry runs through exactly Fibonacci(k+1)-many strings of k digits (through 89 of the
  1,024 strings of 10 digits), a share 0.809^k, so a typical string of k digits waits 1.236^k = 2^(0.306 k) sweeps.
- **Why nothing shortens it.** The sweep is a permutation of the strings of k digits (dropping a carry that
  leaves). (1) Its cycles are short and many: the cycle of 1^k has 2^e strings with e about 0.4 k (2^81 at k = 200).
  (2) In one cycle of 1^k the carries leaving the k digits form a word over a, b, c that the next digit maps to
  the next word (once or twice round); its length shrinks by 0.809 per digit and doubles on about 0.4 of the digits,
  so it grows like 2^(0.1 k): 16,093 letters at k = 140, 817,567 at k = 200. The first carry through 410,984 digits
  is the image of such a word, and no periodicity in k was found in the words or in the times of the carries.
  (3) The powers (sweep)^(2^j), kept as automata with shared states, about triple in size with every squaring
  (233 states for j = 0, 140,903 for j = 10, on 60 digits).

So the event system is exact and proved, but deciding it means following a pseudo-random orbit for about 2^110,000
sweeps: no accelerator was built, and the verdict does not change.

## Where it stands

**Open.** The next overflow needs a carry through 410,984 digits. On small counters the number of sweeps to the next
overflow doubles about every 3 digits, which puts it at the order of 2^(1.3·10^5) sweeps. Whether it is an
extension, a conversion or a halt is not known, and no shortcut was found: the sequence of carry states leaving a
prefix of the counter, kept as a straight-line program, stops compressing after about 150 digits (the program grows
from 5,000 nodes at 100 digits to 7.3·10^6 at 200; `py/events.py program` in the folder of 74982).

Observed on other counters (not proved, and no guide to this one): of 300 random counters of 30 to 60 digits
followed to their first halt or conversion, 170 end in a halt.
