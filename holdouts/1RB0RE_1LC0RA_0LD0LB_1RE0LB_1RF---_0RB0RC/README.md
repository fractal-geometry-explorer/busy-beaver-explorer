# 1RB0RE_1LC0RA_0LD0LB_1RE0LB_1RF---_0RB0RC

bbchallenge id 98520, one of the six-state holdouts (group G06: one side of the tape stops growing, the other grows
like a square root). Whether it halts from blank tape is open. Its tape is a list of nested counters, each a block of ones followed by a block of `10`s; the last one is worked down four ones per sweep, and when it is used up the one before it ticks and a new, about three times longer last block is made.

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 0RE |
| B | 1LC | 0RA |
| C | 0LD | 0LB |
| D | 1RE | 0LB |
| E | 1RF | --- |
| F | 0RB | 0RC |

## What it does

Left of the start nothing grows; the tape grows to the right. After a few million steps it reads, from the left,

```
1^385 (10)^15 0 1^4 (10)^4 0 1^466 (10)^17 0 1^6 (10)^3 0 1^1494 (10)^15 0 ... 0 1^a (10)^b 0 1 0 0 (10)^c  A>
```

a list of segments `1^x (10)^y` separated by single zeros. In each sweep the head runs from the right end to the
last segment and back: four of its ones are eaten, its `10` block gains two, and the end block gains one (`sweep`,
proved for every b, c and any tape to the left). When the ones of the last segment are used up, the head works on the
segment before it, which ticks (four ones fewer, two `10`s more, for example `1^4698 (10)^13` to `1^4694 (10)^15`),
and the `10` blocks on the right are turned back into a new last segment of ones, about three times as long as the
previous one (1,514 to 4,714 ones in the run from blank tape). Earlier segments change more and more rarely, like
the digits of a counter, and short segments are rebuilt into new shapes (`1^11 0 0`, `1^6 (10)^3`).

Both kinds of sweep are proved in Lean for every size (`sweep`, `sweep_p` below). The tape ends either with
`1^x (10)^y 0 1 0 0 (10)^c` (mode Q: four ones per sweep, the end block gains one `10`) or with `1^x (10)^y` (mode P:
two ones per sweep). Everything else is an *event*: the last segment's ones run out, a segment further left ticks,
and a new last segment is built. Events are rare. In the run to 1.4·10^16 steps (`c/accel.c`) there are about 160
events against 1.4·10^8 sweeps.

The events seen so far form a fixed cycle per segment. Here it is for the segment `1^4706 (10)^9` with its
companion `1^0 (10)^4`, in the run from blank tape (each arrow is one event; the batches of sweeps between events
are left out):

```
4706.9 0.4 [0.1179 0.1 0.587] -> 4702.11 2.3 [0.2945]        -> 4698.13 2.4 [5882.5 0.1]
                              -> 4698.13 2.4 [2.2945 0.1 0.1470] -> 4694.15 4.4 [0.7360] -> 4694.15 0.6 [14714.5 0.1]
                              -> 4690.17 10.1 [...]          -> 4690.17 6.3 [14714.5 2.1 ...] -> 4690.17 6.3 14706.9 0.4 [7348.5 0.1]
```

`x.y` is `1^x (10)^y`, and the brackets hold the end of the tape. The segment ticks four times (4 ones fewer, 2
`10`s more each time), while its companion goes through 0.4, 2.3, 2.4, 4.4, 0.6, 10.1 and 6.3. Then it freezes, and
the new last segment of 14,714 ones (about three times 4,706) becomes the next segment of the same kind. Not every
segment takes this path: `14690.17 6.3` and later segments also show companions `2.5`, `6.4` and `2.4` with other
residues. At 7.6·10^15 steps the tape is a list of big segments `1^X (10)^y` (X from 4·10^6 to 5·10^7, y between
11 and 17), each followed by a small companion (`2.3`, `4.4`, `6.3`, `2.4`).

The event cycle is read off the simulation; it is not yet a proved macro rule.

## Status

**Open.** The machine is a hierarchy of counters: a segment ticks once each time the segment after it is used up, and the last one is ticked by the sweeps. It can halt only when the head, working on a segment, meets a configuration that leads to the halting transition (E reading 1); which segment shapes do that is not known. A precise rule for one tick of each segment (in terms of x, y and the shapes of short segments) would turn this into a question about a nested counter, the step before deciding it.

## Proved in Lean

- `lean/Rules.lean` (generated by `lean/rules.py`), shift rules for the pieces of a sweep:
- `wall_right`: B runs right across `(10)^n`, shifting it by one cell.
- `ones_left`: C runs left across `(10)^n` unchanged.
- `fill`: F runs right across `(10)^n`, writing `11`s.
- `sweep`: one sweep of the last segment (mode Q). `L 1 1 1 1 (10)^(b+2) 0 1 0 0 (10)^(c+1) A>` becomes
  `L (10)^(b+4) 0 1 0 0 (10)^(c+2) A>` in 8b + 4c + 38 steps, for any tape L.
- `sweep_p`: one sweep in mode P. `L 1 1 (10)^(b+1) A>` becomes `L (10)^(b+3) A>` in 4b + 10 steps, for any tape L.
- `lean/Blank.lean` (generated): the halting configurations (`step_none_iff`) and no halt in the first 10^7 steps.

## Computed (exact, not proved)

- `c/accel.c`: the run from blank tape. At each sweep end it checks whether `sweep` or `sweep_p` applies and, if so,
  does all the sweeps the last segment's ones allow at once, with the proved step counts. Everything else runs step
  by step.
  - Checked against the plain machine: the tape hash and step count agree at the sweep ends at steps 59,136,370,
    111,168,816 and 2,401,664,914.
  - **No halt in the first 1.39·10^16 steps** (13,977,446,236,662,410). At that point the tape is 272,397,888 cells
    long, and the run took 78 batches covering 136,198,641 sweeps. It takes 10 seconds; the 2 GB tape array is the
    limit.

## For later

- Find which segment shapes lead to the halting transition, and whether the nesting can ever produce them.

## Accelerated run (13 November 2026)

Observed, not proved: the accelerated simulator `rsim.py` ran 6.70x10^523 steps from blank tape without reaching a halting transition. Its tape, state and head position were equal to those of a plain C simulator at 6 checkpoints, the last at 1.38x10^10 steps. Of these steps, the part after the last checkpoint rests on the simulator alone, including 8,682 trip-level jumps: a jump applies many identical round trips at once after seeing the same tape shape recur with constant count changes, which is validated against direct simulation but not proved.
