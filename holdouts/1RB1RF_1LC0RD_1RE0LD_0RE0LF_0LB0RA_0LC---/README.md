# 1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---

bbchallenge id 27281. One of the six-state holdouts whose halting from blank tape is open. Family: Binary counter fed by a work zone (1RB1R?_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC--- twins).

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 1RF |
| B | 1LC | 0RD |
| C | 1RE | 0LD |
| D | 0RE | 0LF |
| E | 0LB | 0RA |
| F | 0LC | --- |

**Verdict.** **The question is open.** It halts only when F reads a 1, which has not happened in 2·10^10 steps. The left end is a binary counter whose increment is proved in Lean; the work zone that drives it is not understood.

## What it does

Twin 2b; the other twin is `1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---`. They differ only in A1 (2a: 1RD, 2b: 1RF); A reads a 1 only 11 (2a) / 17
(2b) times in 10^9 steps, the first at step 132. The family's scripts are in
`holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/`.

- **Left end: a binary counter.** After a fixed prefix (`1010101101010110` for 2a, `10` for 2b): 4-cell digits `1010`
  (one) and `1000` (zero), least significant on the right, ended by `11`. The increment
  `L 1000 (1010)^n C>1 1 R -> L 1010 1 (0001)^n 0 D> R` (12n+8 steps) is proved in Lean for both twins; in
  simulation the decoded value goes up at almost every change over 10^9 steps (2a: 529,571 increases, 4 overflows,
  2 unclassified; 2b: 149,848 increases, 2 width changes).
- **Work zone.** Right of the counter the head zigzags thousands of times between increments in a zone of words `10`,
  `1000`, `110`; a block `(110)^n` at the right end grows slowly.
- The stretches `(0 1)^n`, `(0^3 1)^n` seen earlier are the counter digits read with another phase.

## What is established

**Proved in Lean, kernel only:**

- **The halting configurations.** The machine stops exactly when it reads the symbol of a halting transition (F1); the generated statement covers every configuration. (`step_none_iff`, `lean/Blank.lean`)
- **No halt in the first 10,000 steps.** The list simulator of the shared library, proved to agree with the machine's semantics, runs 10,000 steps from blank tape without a halt, evaluated by Lean's kernel. (`blank_runs_kernel`, `lean/Blank.lean`)
- **Shift rules.** One shift rule for all n and any surrounding tape: B crosses `(100)^n` leaving `(101)^n`. (`lean/Rules.lean`, `holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/py/gen_rules.py`)
- **The increment of the left counter.** For every n and any tape around it, `L 1000 (1010)^n C>1 1 R` reaches `L 1010 1 (0001)^n 0 D> R` in 12n+8 steps: C walks left over n one-digits `1010`, turns the zero-digit `1000` into a one, and B walks back turning each one-digit into a zero-digit. A1 is not used, so the same theorem holds for both twins. (`counter_increment`, `lean/Rules.lean` (generated by `holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/py/gen_rules.py`))

**Proved in Lean with `native_decide`:**

- **No halt in the first 10^7 steps.** The same run, evaluated by compiled code. (`blank_runs_native`, `lean/Blank.lean`)

**Trusted computation (C/Python, not Lean):**

- **No halt in the first 10^9 steps.** The C simulator `tools/c/triage.c` runs 10^9 steps without a halt; at the end 150 cells have been visited and 52 of them hold a 1. (`holdouts/triage.json`)
- **No halt in the first 2·10^10 steps.** Direct simulation with `tools/c/tmrun.c`. (`tmrun 1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC--- 20000000000`)
- **Where the twins differ.** In the first 10^9 steps A reads a 1 only 17 times, always with 0s on both sides; F reads only 0s, followed by a 0 except 16 times. (`holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/c/ctx.c`)
- **A binary counter at the left end.** Whenever the head is at least 8 cells right of the counter, the tape from the left end reads `10`, then 4-cell digits `1010` (one) and `1000` (zero), then `11`. Read as a binary number (least significant digit on the right) this counter goes up at almost every change. From step 1.5·10^7 to 10^9 the decoded value changes 149,850 times; 149,848 are increases and 2 are changes of width (19 → 24 → 26 digits as the script reads them; the counter has 26 digits at the end, with value 19,634,864, about 29% of the way to overflow). (`c/leftsnap.c`, `py/cntchk.py` in holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---)
- **Not decided by n-gram CPS up to width 14.** The n-gram Closed Position Set decider (`tools/c/ngramcps.c`) with equal widths 4, 6, 8, 10, 12 and 14, plain and with the fixed-length (1) and LRU history augmentations, either reaches a halting local configuration (UNKNOWN) or stops at 3·10^7 local configurations: it does not prove non-halting at these settings. (`ngramcps MACHINE N [-H 1 | -U] -m 30000000`)

**Heuristic:**

- **Growth shape: exp/fixed.** Left of the start, the visited part of the tape stopped growing in the second half of the run (bounded so far, or growing so slowly that no record fell in the last half). Right of the start it grows like the logarithm of the step count: each new cell costs a roughly constant factor more time, the signature of a *counter* or of a Collatz-like map whose values are written on the tape (fitted exponent 0.046). (`tools/py/bbtools/triage.py`)
- **Tape structure.** Late in the run the tape is made of long stretches of `(0 1)^n`, `(0^3 1)^n` and `(1^2 0)^n`; both ends grow, the right one by single cells at irregular times (e.g. 2a: cell 175 at step 4.7·10^8). The stretches `(0 1)^n` and `(0^3 1)^n` are the digits 1010 and 1000 of the left binary counter read with another phase (see below).
- **A work zone between the counter and a growing (110)^n block.** Right of the counter the head works in a zone of 20 to 40 cells of words `10`, `1000`, `110`, turning thousands of times between two increments of the counter; at the right end a block `(110)^n` grows by one word at each right record (for 2a, n = 12, 13, 14 at the right records at 4.7·10^8, 5.8·10^8 and 9.6·10^8 steps). What the work zone computes between two increments is not known. (`tools/c/tmrun.c` snapshots)

**Open:**

- **Does it halt from blank tape?.** Not known. No macro description of the run is known yet.

## For later

The work zone: find the configurations it passes through between two increments of the counter (snapshot it each
time C reads the `11` after the counter), and how they depend on the counter's low digits. Its rule decides how fast
the counter runs and when the `(110)^n` block grows, and it is where a halt (F reading 1) would have to happen.

## Reproduce

From the repository root:

```sh
. /etc/profile.d/lean.sh      # after scripts/setup-lean.sh
holdouts/1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/lean/check.sh
python3 holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/py/gen_rules.py 1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC--- H27281 | diff - holdouts/1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/lean/Rules.lean
gcc -O2 -o tmrun tools/c/tmrun.c && ./tmrun 1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC--- 20000000000
gcc -O2 -o leftsnap holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/c/leftsnap.c && ./leftsnap 1RB1RF_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC--- 1000000000 110 > ls.txt && python3 holdouts/1RB1RD_1LC0RD_1RE0LD_0RE0LF_0LB0RA_0LC---/py/cntchk.py ls.txt 2b
```
