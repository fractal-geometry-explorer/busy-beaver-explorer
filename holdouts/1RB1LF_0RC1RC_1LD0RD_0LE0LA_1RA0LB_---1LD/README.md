# 1RB1LF_0RC1RC_1LD0RD_0LE0LA_1RA0LB_---1LD

bbchallenge id 97939. One of the six-state holdouts whose halting from blank tape is open.  It is a
**base-4 counter feeding a stack of timers**.  The left part of the tape is a base-4 counter whose digits are the
words `10`, `1`, `101`, `11` (0 to 3), separated by runs of pairs `110`; every visit of the head to the left end adds
one.  Only when the counter overflows does the head sweep all the way to the right end, through a list of long
blocks of ones that behave like timers: at every such visit the last block loses 9 ones, the one before it 24, the
one before that 96, then about 384.  Its twin is [`1RB1LE_1RC1LF_0RD1RD_1LE0RE_0LA0LB_---1LE`](../1RB1LE_1RC1LF_0RD1RD_1LE0RE_0LA0LB_---1LE/README.md), which runs the same counter and
the same timers (all blocks but the last are equal at every right-end visit, the last differs by 186).

| state | read 0 | read 1 |
|---|---|---|
| A | 1RB | 1LF |
| B | 0RC | 1RC |
| C | 1LD | 0RD |
| D | 0LE | 0LA |
| E | 1RA | 0LB |
| F | --- | 1LD |

## What it does

### The counter (left end)

At each visit of the left end in state D, the tape is `D>0 (110)^n0 d0 (110)^n1 d1 ... (110)^nk dk` followed by
the timer blocks, where each digit `d` is one of `10` (0), `1` (1), `101` (2), `11` (3).  One round, from a visit of
the left end to the next, adds one to the counter (`lean/Rules.lean`, generated by `py/rules.py`, for all run
lengths and any tape `R` to the right):

| round start | next round start | rule |
|---|---|---|
| `(110)^n 10 (110)^m R` | `(110)^(n+1) 1 (110)^m R` | `inc0` |
| `(110)^n 1 (110)^m R` | `(110)^(n+1) 101 (110)^(m-1) R` | `inc1` |
| `(110)^n 101 (110)^m R` | `(110)^(n+1) 11 (110)^m R` | `inc2` |
| `(110)^n 11 (110)^m d R` | `(110)^(n+1) 10 (110)^m (d+1) R` for `d` = 0, 1, 2 | `carry0`, `carry1`, `carry2` |

So the first run of pairs grows by one cell triple per round (the "sqrt" side: a round takes a sweep across the
growing left part), and a carry out of digit `i` happens once every `4^(i+1)` rounds.

### The timers (right end)

379, 283 and 3187, 3091, ..., 2707), the next about 384; the blocks on the left are the counter, written out.  The
right end is reached only at overflows, which come exponentially rarely, so the right side of the tape grows like
the logarithm of the step count (the "exp" side of the triage).  When a timer runs out it is refilled from the
blocks on its left (as 564 becomes 675 at step 2,122,428); how exactly is not yet written down.

### How it could halt

The halting transition is F0: it happens when D reads a 1 whose left neighbour is a 1 with a 0 before it (`0 1 D>1` gives `D1 -> 0LA`, `A1 -> 1LF`, F on the 0).
As in the twin, this is the end of a chain `D1 -> 0LA`, `A1 -> 1LF`, `F1 -> 1LD` that turns each `111` into `110`,
on a run of length 2 mod 3 (the twin's `lean/Chain.lean`).

### It is the twin, started in state B (second pass)

Rename the states A, B, C, D, E, F of the twin `1RB1LE_1RC1LF_0RD1RD_1LE0RE_0LA0LB_---1LE` to E, A, B, C, D, F.
Every transition then agrees with this machine except one: the twin's `A1 -> 1LE` becomes `E1 -> 0LB` here, and
with `B? -> ?RC` (B writes back the symbol it read) and `C0 -> 1LD` these three steps have the same effect as the
twin's one step.  `lean/Twin.lean` proves this step simulation for every configuration and concludes (kernel, no
`native_decide`)

    theorem twin : HaltsFromBlank ↔ TM.Halts trans1 (TM.blankCfg .B)

where `trans1` is the twin's table (with this machine's state names): this machine halts from blank tape exactly
when the twin halts from blank tape started in state B.  (`halts_iff` is the same for every configuration.)  The
two runs differ only in the twin's first step (`A0 -> 1RB` writes one extra 1), presumably why one timer differs by a
constant.  The twin's right-end map (`c/rmap.c` and `py/gencheck.py` there, run with state C here) is the same:
15 random lists checked.
