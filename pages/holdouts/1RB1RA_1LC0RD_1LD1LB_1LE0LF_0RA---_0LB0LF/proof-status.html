OpenNobody has proved whether this machine halts. Everything below is what is known so far.

Nobody knows whether this six-state, two-symbol Turing machine halts when started on a blank tape: it is one of the holdouts left open by the bbchallenge project. This page lists what has been established about it, sorted by what each result rests on.

Status as of 20 November 2026.

In short

The question is open. Up to renaming, the machine is the table of a DeepMind proof (busycoq pull request 93) with its halting transition replaced. A Coq proof built from that file needs only one more thing, a stop of its accelerated engine, and the engine has not stopped in more than 107765 steps. The place where the sibling halts recurs in this run once per lap, and this machine gets past it the same way every time; nothing in the run comes near the one pattern that could halt it.

A halt needs B reading 0 with 0, 0, 1 on its left

E is entered only by D0, D by B1 (which leaves a 0 behind it) or C0, and C only by B0, so the last four steps of a halting run start in state B reading 0 with the cells 0, 0, 1 to its left, nearest first: an internal run of exactly three 0s entered from its right end.

halt_needs_pattern, lean/Halt.lean

A Coq proof that only needs the engine to stop

coq/mkU.py rewrites the DeepMind proof of busycoq pull request 93 for this machine. Up to swapping E and F the machine is that proof's table with F merged into E (so the sibling's halting transition becomes a step) and with D0 replaced by a three-step detour that halts exactly when D reads 0 with a 1 on its left. The file compiles with Coq 8.20.1 and Print Assumptions lists only run_ok, the statement that the engine stops; with it the file would prove that the machine halts.

No halt in the first 107765 steps

The engine of that proof file, extracted to OCaml with Coq's binary numbers realized by Zarith (the same engine as for starts B and D of the table, whose full compressed states equal those of the plain extraction at fast steps 35,227,304 and 29,077,778 of those runs; the plain extraction was checked against direct simulation through 3×109 steps), ran 601,531,739 fast steps from blank tape without stopping (22 November 2026). Its tape then has more than 225798 cells, each visited at least once. Every entry into raw mode (where a halt would have to happen; the engine checks each raw step for one) falls into the same few classes as in the earlier runs: D moving right with a 0 on its left, D moving left onto a 1, B moving right, or the sibling’s halting event (C reading 0 with 1 1 1 on its left), which this machine survives each time.

heuristic Evidence only

Growth shape: exp/sqrt

Left of the start, the visited part of the tape grows like the logarithm of the step count: each new cell costs a roughly constant factor more time, the signature of a counter or of a Collatz-like map whose values are written on the tape (fitted exponent 0.115). Right of the start it grows like the square root of the step count, the signature of a head sweeping back and forth across the whole tape and adding a cell or a few at the end of each sweep (a bouncer-like shape) (fitted exponent 0.503).

tools/py/bbtools/triage.py

A marker sweeping left

Between round ends the head goes back and forth across most of the tape; the point where it turns moves left a few cells per trip while each trip adds a few cells on the right. This is why the right side grows like the square root of the step count and the left side, which only grows at round ends, like its logarithm.

No halt in the first 2.33×1014 steps of an accelerated run

Observed, not proved: the accelerated simulator rsim.py ran 2.33×1014 steps from blank tape without reaching a halting transition. Its tape, state and head position were equal to those of a plain C simulator at 6 checkpoints, the last at 1.00×1010 steps. Of these steps, the part after the last checkpoint rests on the simulator alone, including 6,537 trip-level jumps: a jump applies many identical round trips at once after seeing the same tape shape recur with constant count changes, which is validated against direct simulation but not proved.

The sibling's halting point recurs and is survived

A halt can only happen where the engine leaves its macro rules. Through 18.4 million fast steps it left them only in 14 kinds of local situation, all at the left end of the written tape. One of them, C reading 0 with 1 1 1 on its left, is exactly where the sibling of pull request 93 halts; here it recurred 10 times, with the same nearest cells each time, and each time the machine erased three 1s and went back to the macro rules. No exit met the cells 0, 1 that a halt needs. So the sibling's halting point predicts no halting point for this machine, and a halt would need a kind of exit the run has never produced.

Does it halt from blank tape?

Not known. The Coq file above would settle it if the engine ever stopped; a proof that it never halts would need the closed form of the DeepMind counter's laps, including that no lap ever ends in the three-0 pattern.
