A 6-state Busy Beaver machine · Status as of 8 November 2026.

Does this machine ever halt?

1RB1LF_1RC1RB_1RD0RB_0LE0LF_---1LD_0LE1LA

Nobody knows yet, but the one way it can stop is known, and the run has been followed exactly for 1018 steps. The tape is a row of blocks: runs of 01 pairs that grow and runs of 1s that shrink, a little at each sweep of the head. When a run of 1s is used up, its two neighbours merge in a zigzag, and a merge at the left end halts the machine if its left block is too short. So far the right block has never been even half as long as the left one.

The machine

6 states, two symbols, 1 halting transition

Each entry says what to write, which way to move and which state to enter. The machine starts in A on a blank tape (all 0s).

The machine stops when it is in E reading 0. E is entered only from D0 (writes 0, moves L): 0 D>0; F0 (writes 0, moves L): 0 F>0. So a halt is the moment one of these patterns appears, with the head on the cell after >.

Tape as words

A row of growing and shrinking blocks

Stop the machine each time the head is at the left end of the tape (in state A). The tape then always reads

(01)^x0 (1)^y1 (01)^x1 (1)^y2 (01)^x2 … (1)^yk (01)^xk · short tail

for example, at step 9,999,886,792:

(01)^38561 (1)^14643 (01)^10801 (1)^8987 (01)^1723 (1)^3639 (01)^112 (1)^23 (01)^29 (1)^55 (01)^6 (1)^9 (01)^3 1 0 1 0 0 1 0

Between two visits of the left end the head runs right (state B turns every 01 into 10 and passes over 1s), bounces near the right end and comes back (A and F walk over 1s, E and D over pairs). The net effect of one round trip is simple:

blockafter one round trip
(01)^x(01)^(x+1)
(1)^y(1)^(y−2)

Each boundary moves two cells to the right, so the length of every pair of blocks, 2x + y, stays the same. The short tail at the right end keeps making new small blocks; the same tail patterns recur over and over, so the small blocks are recycled the way low digits of a counter are.

Each separator between two blocks of pairs lives the same life: 1^y → 1^(y−2) → … → 1 → [0] → [10] → merge, where [0] is a single 0 cell and [10] the cells 1 0. The head going right turns back at the first [0], so for one round trip the part of the tape beyond it is not swept. A stretch at the left end ((x) stands for (01)^x):

steptape at the left end

11,671(42) [10] (13) 1^3 (7) 1 (3) …

In the last line the merge has happened: 42 − 13 = 29 pairs are left of the new block of ones, which has 4·13 + 3 = 55 cells.

Macro rule

When a run of 1s runs out: the merge

The 1-block with the smallest y empties first. Then the head stops making full round trips and zigzags on the spot: each zigzag takes one pair from the block on the left and one from the block on the right and adds four 1s in between,

(01)^(a+1) A>0 1 (11)^n 0 (01)^(k+1) → (01)^a A>0 1 (11)^(n+2) 0 (01)^k   (4n+10 steps)

(proved in Lean for all a, n, k). When the right block (01)^b is used up the zigzag stops and normal sweeping resumes:

(01)^a [empty] (01)^b (1)^c → (01)^(a−b) (1)^(4b+c)

Example (step 438,516): (01)^261 1 0 (01)^82 (1)^81 becomes (01)^180 (1)^409: 261 − 82 = 179 plus the pair gained on that round trip, and 4·82 + 81 = 409.

Exact model

A block machine proved to follow the machine

The description above is a reading of a simpler object that Lean checks completely. Cut the tape into blocks of two cells and store each side of the head as a list of runs (block, count), so 01 01 01 … is one entry 01^x. One step of this block machine looks up what the machine does on the block in front of the head (it leaves the block to the right or to the left in some state, having rewritten it; 48 cases for each side, each one checked by Lean). If the head leaves on the far side in the state it came in with, it would do the same on every copy, so the whole run of equal blocks is crossed in one step.

Lean proves for every configuration that each block-machine step is a run of the real machine and that a block-machine halt is a real halt, starting from the blank tape. So the block machine is an exact abstract machine for the whole run, not an approximation: the blocks (01)^x and (1)^y are its runs 01^x, 10^x and 11^m.

It is fast because a sweep over a block of a million pairs is a single step. Evaluated inside Lean it certifies 124,890,717,366 steps without a halt; the same machine written in C reaches 1010 steps in 0.03 seconds and 1018 in about eight minutes.

Halting

The one way to halt

The merge needs a > b: the block on the left must outlast the block on the right. If the left block runs out first, the zigzag walks into whatever lies further left. At the left end of the tape that is 1 1 1 and then blank tape, and Lean proves (kernel only, every a, n, k) that

0^∞ 1 1 1 (01)^a A>0 1 (11)^n 0 (01)^(a+k+2) …  halts:

after a zigzags the left block is gone, the head runs left over the ones in state F, reads the blank cell, and E on a 0 is the halting transition. Simulating real tapes with the left block shortened confirms it: with the right block 28, every left block up to 28 halts.

So does the left block always win? At the 23 left-end merges of the first 1010 steps the left block was 2.9 to 4.3 times the right one:

There is also a margin for the future. Right after a left-end merge the new left block is X0 − X1 and the new right block is the next block X2; until the next left-end merge the difference between them can only grow (both gain a pair per sweep and merges further right only shorten the right one). So a merge with X0 − X1 > X2 makes the next one safe, and in the run (X0 − X1)/X2 was always at least 5.8 (to 2·1017 steps).

Why this is not yet a proof

Follow each block of ones in coordinates that move with it: its left end minus the time and its right end plus the time. These two numbers stay fixed between merges. A merge mirrors the left end of the next block about the point where the vanished block closed, and the machine halts exactly when such a mirror image passes the left end of the tape. New small blocks keep arriving from the right end, and merges cascade from the right towards the left, the left block growing by a factor of about 1.3 to 1.5 each time (often exactly 3/2 up to rounding).

So the question is about a deterministic cascade that looks roughly the same at every scale, like the Collatz-type questions behind other holdouts. Simple inequalities do not close up: each block of pairs is longer than all later ones together holds throughout the run and survives merges, but the sweeps break it; the blocks of pairs get shorter to the right survives sweeps but not merges. A proof of non-halting needs an invariant of the whole cascade.

Each left-end merge protects the next one

With X0, X1, X2 the first three blocks of pairs at a left-end merge, the next left-end merge is safe if X0 − X1 > X2, because X0 − X1 never decreases between two left-end merges (an argument from the sweep and merge laws; checked at 11,085,706 consecutive left-end visits to 1015 steps, one exception at step 2,871 with blocks of at most 10 pairs). At every left-end merge with X0 ≥ 100 up to 2·1017 steps (47 merges), (X0 − X1)/X2 was at least 5.8.

Heuristic
README, Why it is hard
A roughly self-similar cascade

From one left-end merge to the next the left block grows by a factor of 1.3 to 1.5 (often exactly 3/2 up to rounding: 571,835, 857,753, 1,286,629) and follows X0' = X0 + X1 + m2 (±1). Each block of pairs is longer than all later ones together at every left-end visit (smallest ratio 1.65 to 1014 steps), but neither this nor any simple inequality on the blocks survives both sweeps and merges, so it is not an inductive invariant.

Open
Does it halt from blank tape?

Not known. The machine halts if a merge at the left end ever meets a right block not shorter than the left one (by 2). The block machine of lean/Macro.lean is exact, so a halt would show up in it; a proof of non-halting needs an invariant of the whole cascade of merges, which is not known.
