Does this machine ever halt?

1RB---_1LC1RE_0LD0LC_1RD0RB_1RF0RB_0LF1RA

Nobody knows whether it halts. It counts in binary twice at once: a counter at the right end, three cells a digit, and a bit string in the single 0s between the blocks on its left. That part is proved in Lean for every size, so it can only halt when the bit string overflows; how an overflow rebuilds the tape is the missing piece.

The machine

6 states, two symbols, 1 halting transition

Each entry says what to write, which way to move and which state to enter. The machine starts in A on a blank tape (all 0s).

The machine stops when it is in A reading 1. A is entered only from F1 (writes 1, moves R): F>1 1. So a halt is the moment this pattern appears, with the head on the cell after >.

The picture

Two binary counters

Every so often the head arrives at the right end of the tape in state E, on blank: an event. The tape is then blocks of 1s split by single 0s, the last one long: 1^x1 0 … 0 1^N E>0. The last block is a binary counter with digits three cells wide; between events it counts to 2j, j = (N+2)/3, and comes back three cells longer. The blocks on the left are a second counter: after the first two 1s the cells come in pairs (separator, 1) and a separator that is a 1 is a set bit. Each event adds 2j to it. The Lean proof of that machine's event rule (lean/Count.lean: one count, 2d counts by induction, the phase) carries over with the states renamed, so the rule holds for every size here too.

Overflow

Overflows

When adding 2j carries out of the top bit, the tape is rebuilt. The run to 4·1011 steps has three overflows:

Unlike in 1RB---_1RC0RD_1RD1RA_1LE1RB_0LF0LE_1RF0RD, N goes back to 1 or 7 and a block of four 1s can appear for one event; no formula for the rebuilt string is known.

Halting

The one way to halt

Run directly on every bit string of 4, 5 or 6 bits with every j ≤ M, the machine halts only when all bits are set and j = M: the tape 1^(2M+2) 0 1^(3M−2) E>0. Lean checks that these halt for M = 4, 5, 6 (after 746, 1,514 and 3,050 steps). Within a phase the bits below the current position j never change again, so the string can be all ones at the top only if those bits already are. The current phase started at step 1,491,439 with 36 bits and j = 3; at step 206,159,921,357 it has reached j = 33, and the 33 bits below, 000000000011011011000011010101111, hold 0s: this phase cannot halt. It overflows after j = 35, near step 1.6·1012.

Next steps

The overflow rule. py/accel.py (in the folder of 1RB---_1RC0RD_1RD1RA_1LE1RB_0LF0LE_1RF0RD) follows the run exactly: jumps between overflows whose endpoints are proved (step counts checked against the direct run), and only the overflows simulated cell by cell. It reaches the third overflow at step 1,649,096,662,853, which leaves a 47-bit string with d = 28; the fourth is about 1015 steps away. Collecting overflows from small cases (all 240 overflowing phases with at most 6 bits) shows the next phase starting with d = 0 in 219 cases and a string 4 to 17 bits longer, in a way that depends on more than the low bits; a formula like the other machine's has not been found. The only small cases that halt are the phases that end in the all-ones pattern.

First look

The shape of the run

Left of the start, the visited part of the tape stopped growing in the second half of the run (bounded so far, or growing so slowly that no record fell in the last half). Right of the start it grows like the logarithm of the step count: each new cell costs a roughly constant factor more time, the signature of a counter or of a Collatz-like map whose values are written on the tape (fitted exponent 0.032).

After 109 steps the tape spans 151 cells (7 left of the start, 140 right), with a density of 1s of 0.49.

The tape (run-length coded, 1^5 is five 1s, C>0 the head in state C on a 0) at some of the last moments the head reached a new cell, cut to 400 characters:

Kernel
event_rule, lean/Count.lean; 1RB---_1RC0RD_1RD1RA_1LE1RB_0LF0LE_1RF0RD/py/pchain.py
The event rule, for every size

This machine is 1RB---_1RC0RD_1RD1RA_1LE1RB_0LF0LE_1RF0RD with one transition changed: with the states renamed (B, C, D, E, F there are E, F, B, C, D here) the tables agree except that machine's C0 = 1RD, here F0 = 0LF. In the counting phase that transition is used only on a counter digit, E> 0 0 x (E0 1RF, F0 0LF, F1 1RA, A0 1RB, then B on x), which does what the other machine does in 5 steps instead of 3. So the proof of lean/Count.lean carries over with the states renamed and two step counts changed: count, iter and event_rule (from P(d, b1 :: lo ++ h) to P(d+1, b1 :: lo ++ inc h) when lo has d bits and h has a 0), event_to_P, and blank_to_P (the run reaches P(0, 1100111) at step 311). Every pair of consecutive P configurations of a run to 2·107 steps follows the rule (33) or is an overflow (2).

Kernel
event_rule, lean/Count.lean
Halting only at an overflow

Follows from blank_to_P and event_rule (the deduction is not itself a Lean theorem): the run from blank reaches a P configuration and the rules are runs, so the machine can halt only in a phase P(d, bs) whose addition of 2d+1 carries out of the top bit.

In a phase the bits below the current position j never change again. In the phase from step 1,491,439 the event at step 206,159,921,357 has j = 33 and its 33 bits below j (000000000011011011000011010101111) include 0s, so the string never becomes all ones in this phase; it ends with an overflow after j = 35, near step 1.6·1012 (the time per event doubles). The overflow rule

What an overflow writes is not known as a formula. By direct simulation of all 240 overflowing phases P(d, bs) with at most 6 bits, the next P configuration has d = 0 in 219 cases (1 to 3 in the others) and a string 4 to 17 bits longer (mostly 5 to 12), in a way that depends on more than the low bits of R; the only 5 that halt are P(M−2, 10…01), the phases that end in the all-ones halting pattern. The exact accelerated run gives the real overflows but no rule.
