Does this machine ever halt?

1RB0RC_1LA0LD_1RB0RD_1LE0RF_0LB0RB_1RC---

Decided: it never haltsProved in this repository, checked by Lean and by Coq. The ledger below says what each part rests on.

No. For its first 1.67×1010 steps this machine goes through five ever longer epochs; then it settles into an exact repeating pattern, a bouncer: the head sweeps between the two ends, and every two sweeps one more block of 13 cells appears on the left while a fixed stretch of 222,182 cells is carried along. Lean proves that the pattern repeats for ever and, chunk by chunk, that the run from blank tape gets there.

The machine

6 states, two symbols, 1 halting transition

Each entry says what to write, which way to move and which state to enter. The machine starts in A on a blank tape (all 0s).

The machine stops when it is in F reading 1. F is entered only from D1 (writes 0, moves R): D>1 1. So a halt is the moment this pattern appears, with the head on the cell after >.

Five levels

From six states to one number

"Does this machine halt?" can be asked at five levels of description. Each level keeps less detail than the one above it and counts time in bigger units, and each step down the ladder is a theorem in Lean saying that the answer does not change. The machine itself is level 1. Level 2 cuts the tape into blocks of 16 cells and moves a block at a time; that is how Lean checks the first 16,730,681,219 steps. From there on the tape has a fixed form, C k, and three more levels describe it: the five pieces of a period, the period itself, and finally just the number k, which goes up by one every period, for ever.

The shape of the run

Left of the start, the visited part of the tape stopped growing in the second half of the run (bounded so far, or growing so slowly that no record fell in the last half). Level 1 to level 2

Blocks of 16 cells

The first 16,730,681,219 steps are checked in Lean by running them. Run one cell at a time this would be slow, so lean/Block.lean cuts the tape into blocks of 16 cells, each kept as a number from 0 to 65,535 (cell i of a block is bit i). A configuration of the block machine, MC, is the list of blocks left of the head, the list from the head on, the state, and whether the head is on the first cell of its block or on the last.

A table tbl has one entry for each state, block and side of entry: 6 · 216 · 2 = 786,432 entries. An entry says what the machine does inside the block until the head leaves it: the new block, the new state, the side it leaves on and the number of steps. It is computed by brun, a run on the block's 16 cells alone, and brun_ok proves that such a run is a run of the machine whatever lies outside the block. The simulator msim makes one table lookup per block crossing; chkF then makes the few steps that are left one at a time and compares the result with a given configuration.

Kernel chkF_ok: if chkF returns true for a start c, a step count t and an end g, then steps t (sem c) = some g.toCfg, a statement about the machine itself. native_decide tblOk: every entry of the table is what mkEntry computes (20 s). Neither needs anyone to trust the table.

  Levels 3 to 5: the form
  
What the tape is made of


From step 16,730,681,219 on, every second time the head comes back to the left end the tape is


C k = 0^inf A> 0 (1010001000100)^k X 0^inf



The head, in state A, stands on the leftmost cell. Then come k copies of the block 10 1000 1000 100 (13 cells), then a stretch X of 222,182 cells that is always the same. X is what is left of the earlier epochs: an irregular record of 10s, 100s and 1000s that the sweeps rewrite on the way out and restore on the way back.


Over one period (two sweeps) the left end moves 4 cells left, one block is added, and X ends up 9 cells further right, so the right end grows 9 cells per period. The time per period grows by 184 steps per block, so the tape grows like the square root of the step count, the bouncer signature.

  Level 3 to level 4
  
The excursions, computed once for every n




An excursion is three million steps over a fixed list of cells, so Lean simply runs it. The difficulty is that the
tape left of X holds the blocks, whose number n is a variable. lean/Window.lean solves this with a list
simulator on a window: wsteps n ⟨l, r, s⟩ runs the machine on the cells l (left of
the head, nearest first) and r (from the head on, blank beyond its end), and fails if the head would move
left of l. Kernel wsteps_over (with wsteps_over1 and
wsteps_over3 for windows of one and three cells): a run on the window that succeeds is a run of the
machine with any tape at all further left. So a single evaluation covers every n.


native_decide The three facts of lean/Period.lean that are evaluated:




theorem w1_ok : wsteps 1517479 ⟨[true], X, .B⟩ = some ⟨[], false :: r1t, .E⟩
theorem w2_ok : wsteps 1511551 ⟨[true, true, false], r1t, .B⟩ = some ⟨[], false :: r2t, .E⟩
theorem close : [true, false] ++ r2t = accb ++ X




The first excursion starts with the head on the first cell of X in state B and the 1 written by pass 1 as its whole
window on the left; it ends with that window used up, the head back on that cell, now a 0, in state E. The second
starts with the three cells 0 1 1 written by pass 2. The last fact says that what the second excursion
leaves behind, behind the two cells 1 0 that pass 3 writes in front of it, is one more block
1010001000100 followed by X again. period chains the five pieces with these facts, and
rep_rotate moves the new block to the front:
1 0 (1000100010010)^(n+1) = (1010001000100)^(n+1) 1 0. Then C (n+1) reaches
C (n+2) in 184n + 3,029,224 steps, for every n.

  Level 5
  
The number k




At the bottom of the ladder the tape is gone. What is left is one number, k, the count of blocks in front of X,
and a clock. The whole proof after step 16,730,681,219 is one rule applied again and again: C k becomes C (k+1),
and the clock moves on by 184k + 3,029,040 steps. native_decide runs_C and
not_halts_C (lean/Period.lean) turn period into "from any C (m+1) the run goes
on for ever", and nonhalt_of_reach into "if the run from blank tape reaches some C (m+1), the machine
does not halt". The run reaches C 7 (reach_C7).


Here the rule is applied to the numbers alone: each press adds one block and adds the rule's step count. Nothing
else on the tape changes, which is why the machine can never meet the pattern that halts it.



  


The clock, and the machine against it


Summed, the rule says that C k is reached at step 16,730,681,219 + 3,029,040 (k − 7) + 92 (k(k − 1) − 42)
for every k ≥ 7. Type any k. The C simulator py/dumpT.c found C 1397 at step 21,120,462,459 (computed,
not part of the proof), as the formula predicts. The button runs the real machine in the browser from C 7 and
records each step at which the tape is exactly C k.

  Aside: before the bouncer
  
How it gets there: five epochs


Before the bouncer the leftward sweeps do not always reach the left end. The cell where they turn back (green below) creeps right, about 7 cells per sweep, while the right end (red) gains 4.5 cells per sweep; when the turning point catches up with the right end it runs back to the left end, and the next epoch starts. Five epochs, each about 3.7 times longer than the last, end at sweeps 250, 950, 3,600, 13,350 and 49,300. After the fifth the turning point stays at the left end: the tape is then C 7, and the period above repeats from there on.



Logged every 200 sweeps by py/lturn.c up to 1011 steps (84,927 sweeps). After sweep 49,300 the step counts of the turns follow a quadratic exactly.

  The bottom line
  
It never halts




It never halts.


Started on a blank tape, 1RB0RC_1LA0LD_1RB0RD_1LE0RF_0LB0RB_1RC--- runs for ever. Lean states it as




theorem nonhalting : ¬ HaltsFromBlank := nonhalt_of_reach (m := 6) reach_C7      -- lean/Reach.lean




where HaltsFromBlank is the machine's own halting from blank tape, defined from its transition table in
lean/Machine.lean. In words: the run from blank tape is at C 7 after 16,730,681,219 steps, and from any
C k with k ≥ 1 it reaches C (k+1), and so on without end.


Why a halt cannot come


The only halting transition is F reading 1. State F is entered only from D reading 1 (D1 = 0RF), so a
halt needs the head in state D on 1 1. In the bouncer phase this never happens: the period is proved for
every number of blocks, and the run over X is the same every time. Before it, Lean checks the whole run of
16,730,681,219 steps from blank tape, in eight chunks of about 2×109 steps: the C simulator proposes
the configurations at the chunk boundaries, and a block simulator proved correct in Lean (blocks of 16 cells, one
table lookup per block crossing) checks each chunk, with native_decide.


What it rests on


#print axioms nonhalting (lean/Axioms.lean) shows the standard axioms and, besides them,
the compiled evaluations of native_decide (Lean.ofReduceBool). So the result is
native_decide: it trusts Lean's compiler for these fixed computations, and the kernel for
everything else.
