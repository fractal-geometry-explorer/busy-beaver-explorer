A 6-state Busy Beaver machine · Status as of 9 November 2026.

Does this machine ever halt?

1RB0LC_1RC1RE_1RD0RA_0LE0RF_1RA0LD_1LD---

Nobody knows yet, but we know what it is doing: it counts. The tape is a row of blocks of ones, each block a digit, and once per trip of the head the number goes up by one. Now and then a carry falls off the left end and the machine starts counting inside its own count. Lean proves every ordinary trip, the inner trips of that nested count, and the one nested count of the run so far: no halt in 4·1014 steps.

The machine

6 states, two symbols, 1 halting transition

Each entry says what to write, which way to move and which state to enter. The machine starts in A on a blank tape (all 0s).

The machine stops when it is in F reading 1. F is entered only from D1 (writes 0, moves R): D>1 1. So a halt is the moment this pattern appears, with the head on the cell after >.

First look

The shape of the run

Left of the start, the visited part of the tape stopped growing in the second half of the run (bounded so far, or growing so slowly that no record fell in the last half). Right of the start it grows like the square root of the step count, the signature of a head sweeping back and forth across the whole tape and adding a cell or a few at the end of each sweep (a bouncer-like shape) (fitted exponent 0.539).

After 109 steps the tape spans 57,779 cells (23 left of the start, 42,386 right), with a density of 1s of 0.559.

The parts

What the tape is made of

Cut the tape at its 0s. Every piece is a block of ones, and almost every block has 2, 5, 8, 11, … ones: 3d+2 ones for a whole number d. Call that block the digit d. Only the leftmost block (three ones for most of the run) is not a digit.

Above: the leftmost block, then the digits 0, 2, 1, 1, then the right end 0 1 with the head (outlined) in state B. Most of the tape is digit 1 (1^5): a long run of them fills the right part and grows by one every two trips. The interesting digits sit in a few short clusters.

The motion

One trip of the head

From the right end the head walks left, rewriting each block it crosses as alternating 0 1. A block of odd length is crossed; the first block of even length (an even digit) stops it. There it turns, walks back to the right end and rebuilds every block it crossed, now three cells further right. So every trip adds exactly three cells.

Above: the digits 1 0 3 1. The left pass crosses 1 and 3 (odd), stops at the 0; the 0 merges into the 1 on its left, which becomes 3; the crossed 3 comes back as 0 0 1 and the 1 as 1. Exactly (for all values, proved in Lean): with a the digit left of the stop digit b and odd digits 2k+1 after it,

stop digitbeforeafter
b = 0a 0 (2k₁+1) … (2kₙ+1)(a+2) 0^(2k₁) 1 … 0^(2kₙ) 1
b = 2i+2a b (2k₁+1) …(a+1) 0^(b−1) 1 0^(2k₁) 1 …

The trip takes 21 + 10b + Σ(20k + 16) steps: it is linear in the length of the tape it crosses, so the n-th trip takes about 8n steps and the run is quadratic: the square-root growth of the tape.

The meaning

An odometer

Read it like a car's odometer. The rightmost even digit is the one that moves. Odd digits to its right are like the 9s in 1999 + 1: the increment turns each of them into zeros and a 1 and carries on to the left. A long run of 1s is a run of carries already made, crossed for free. Five consecutive trips at the right end of the counter, around step 3.9·106:

2… 1 0 1 2 1^491
3… 1 0 2 0 1^492

Each trip adds one unit (three cells). Carries travel left through the clusters and, rarely, reach the left end of the tape: in the run at trips 1,295, 3,343, 4,367 and 5,391, every 1,024 trips while there is one cluster.

The rare event

At the left end: counting inside the count

When no even digit is left, the head reaches the leftmost block 1^r. If the first digit is even it merges into that block (r grows by 6 or 3). If every digit is odd the carry falls off the end: for r = 3 the tape grows three cells to the left and gets two new leading zeros, for r = 9, 15, 21, … the block shrinks back to three ones and leaves zeros behind. All of this is proved.

If r is even (6, 12, 18, …) something new happens: a nested run. Next section.

Counting inside the count

The nested run

On its way left the head has rewritten every digit it passed (a digit 1 becomes the word 0 0 1 0 1 0). At an even leftmost block 1^(6j+6) it does not go back to the right end. The block becomes 1^3 followed by 2j+1 digits 0, and the head turns at a frontier just left of the passed region. Left of the frontier is a new, small counter; right of it the passed region plays the part that blank tape plays for the outer counter.

Lean proves that every inner trip changes the inner digits by exactly the same rule as an ordinary trip, that the inner right end alternates between two shapes, 0 1 1 E>1 0 and 0 1 1 1 0 F>0 1 0, and that every second inner trip eats one passed digit 1: the inner counter grows into the passed region three cells per trip, as the outer counter grows into blank tape. Not yet proved: passed digits 3, 5, … (eaten in another pattern), the inner counter’s own left-end events (which can start a nested run inside the nested run), and the end, when the passed region is used up and the right end comes out in its second shape 0 1^4 B>0.

In the run from blank tape this has happened once, at trip 5,391: from 1^12 | 1 3 1^5 3 1^2686 to 1^15 | 2 0 0 1^6 0 2 1^2686 in 115,676,475 steps, which Lean checks cell by cell.

Far ahead

The long run

After the nested run the digits form clusters separated by long runs of 1s, and runs of 1s are passed unchanged, so each cluster counts on its own and carries only rarely into the next. At trip 109 (step 4·1018):

2 0 0 1^6 0 2  1^2657  2 1 1 0 2 1 1 0 1 2 1 0 2 0 2 1 0 1 2 0 2 0 1^7 2  1^499999999

The run of 1s next to the fixed left part is eaten by about three digits per factor 10 of trips, and a carry reaches the left end only when no even digit is left anywhere. The proved trip rules, run in C on run-length coded digits, go 2.1·109 trips, to step 1.8·1019, without another nested run; at that rate the next one is around 10800 trips away.

The question

Where it could halt

The only missing transition is F reading a 1. Following the table backwards, the machine halts exactly when B reads a 0 followed by 0 1 1: a head moving right meets 0 0 1 1. No proved trip ever shows it that pattern, and Lean proves the consequence: a halt needs the counter to reach another nested run. The open question is whether a nested run, which can contain nested runs of its own, always ends cleanly.

The proof so far

What is proved

Lean, kernel. The pieces of a trip (lean/Rules.lean); a whole trip for every digit list (sweep_zero, sweep_even); the left-end cases except the nested run (raw_zero, raw_even, carry3_sweep, carry9_sweep, phase2_sweep); the trips on run-length coded digits (nextR_sound, lean/Rle.lean); the start of a nested run and its inner trips (nest_sweep, inner_X_zero, …, lean/Inner.lean); the reduction halts_imp_uncovered (lean/Reduce.lean).

Lean, native_decide. The first nested run cell by cell (nested_run, lean/Nested.lean) and 107 trips after it: no halt in the first 400,000,471,326,994 steps (no_halt_long, lean/RunLong.lean).

Trusted (C). c/dsim.c: the proved trip rules up to step 1.8·1019, no uncovered trip.

Open. The nested run as a whole, and whether nested runs always end cleanly.

halts_imp_uncovered, lean/Reduce.lean
A halt needs another nested run

Every sweep takes at least one step, so if the sweep program never stopped the machine would run forever: if the machine halts, the counter, run from step 231,327,122, reaches a sweep the proved rules do not cover (a carry into a leftmost block whose length is not 3 or 6j+9, or the other phase with a last digit other than 1). Rests on reach_B (native).

Kernel
lean/Inner.lean, lean/InnerRules.lean
Inside a nested run: the same counter

A carry through odd digits, the first one 1, into 1^(6j+6) turns the block into 1^3 and 2j+1 digits 0 and turns the head back before the right end (nest_sweep). From there the inner sweeps change the digits by exactly the outer rule (shared core core_zero, core_even with any tape right of the pass), their right end alternates between two phases, and every second sweep eats one passed digit 1 of the region on the right (inner_X_zero, inner_X_even, inner_Y_zero, inner_Y_even).

Heuristic
README, section The nested run
The rest of a nested run

Passed digits 3, 5, … are eaten in another phase pattern (with right ends closing a block 1^4); the inner counter has its own left-end events, including nested runs inside the nested run (seen at depth 2); the run ends with the right end in its other phase when the passed region is used up, and when a deeper level ends first the rest of the region above it is closed into one large digit. Seen in simulation (py/nested_view.py), not formalized.

Heuristic
README, section The long run
When the next nested run could come

After the first nested run the digits form clusters separated by long runs of 1s; the left end is reached only when no even digit is left. The run of 1s next to the fixed left part (2,686 digits) is eaten by about three digits per factor 10 of sweeps (2,656 left at sweep 2.1·109), so the next nested run is very far away (extrapolated, around 10800 sweeps).

Heuristic
README, section Where it could halt
Where a halt would come from

Following the table backwards, the machine halts exactly when B reads a 0 followed by 0 1 1 (a right-moving head meeting 0 0 1 1). No proved sweep produces it; by halts_imp_uncovered a halt can only come from a later nested run.

Open
Does it halt from blank tape?

Not known. Closing it needs the whole nested run as a theorem (inner left-end events, which can start deeper nested runs; passed digits other than 1; the end of the run), so that the sweep program is total, and then an argument that nested runs, which come at ever longer intervals, always end in a sweep configuration.
