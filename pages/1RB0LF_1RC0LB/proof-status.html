Busy Beaver Explorer / 1RB0LF_1RC0LB

What is known about 1RB0LF_1RC0LB, and what is open

1RB0LF_1RC0LB_1RD1RB_1RE1RF_1LA---_0RC1LA

Nobody knows whether this six-state, two-symbol Turing machine halts when started on a blank tape. This page tracks what has been established about it, sorted by what each result rests on.

The run is a sequence of passes: the head fills a sparse region into solid 1s moving right, and turns solid blocks back into alternating cells moving left. Lean proves which passes halt, and that from pass start to pass start the run is a macro machine on a stack and a list of segment and gap lengths; the machine halts only if that macro machine gets stuck.

Status as of 2 November 2026.

In short

The question is open. Lean proves no halt in the first 20,000 steps by the kernel alone and in the first 107 steps with native_decide; the C simulator finds no halt in the first 1010 steps.

Where a halt would come from. Every rightward run is a pass that crosses gaps (runs of 0s between two 1s) of length 1 and 2 and stops at the first other gap. Lean proves that the pass halts exactly when that gap has length 3 (pass_outcome, kernel).

Why it has not halted. Lean proves that the run is a macro machine on lists of numbers, and that the machine halts only if the macro machine gets stuck. That needs two 1s side by side next to an empty segment, which only odd numbers can bring about; in the run they are rare (at most 4 at a time), and the macro machine has never been stuck in 1010 steps.

The halting configurations

The machine stops exactly in state E reading a 1, and D>0 1 halts after one more ordinary step, whatever the rest of the tape.

No halt in the first 20,000 steps

The list simulator of the shared library, proved to agree with the machine's semantics, runs 20,000 steps from blank tape without a halt, evaluated by Lean's kernel. At step 63 the tape is 0 1^2 0 1^4 C>0 (blank_at_63).

blank_runs_20000, blank_at_63, lean/Blank.lean

Which passes halt

A pass starts when F or B reads a 0 and moves right; C then crosses every gap of length 1 or 2 (by induction over any list of them). The first gap of another length ends the pass: a gap of 3 halts, a gap of 4 or more turns left at E, two 1s side by side turn left at B or F. So a pass halts exactly when the first gap it meets that is not 1 or 2 has length 3.

pass, pass_outcome, start_F, start_B, lean/Pass.lean

The leftward pieces

A and F turn 1^(2k) A>1 into A>1 (1 0)^k; B erases 1^k; at the 0 left of a block an odd block starts a pass and an even block starts B erasing the block before it.

sweep, sweep_end_odd, sweep_end_even, erase, erase_end, lean/Pass.lean

The macro machine

At every pass start the tape is a stack of solid blocks 1^(2s+2) separated by single 0s, the head on a gap of 2h+2 cells, and a word of segments (0 1)^m and gaps 0^(2g) 1. A function mstep on these numbers gives the next pass start, and Lean proves the machine goes there, for all values of the parameters. mstep fails only at a gap g = 0 (two 1s side by side) next to an empty segment. So if the macro machine never gets stuck from the configuration after 12 steps, the machine never halts.

mstep_sound, blank_to_M0, no_halt_of_macro, lean/Macro.lean

No halt in the first 1010 steps

The shared C simulator runs 1010 steps from blank tape without a halt; the tape then holds 313 ones and the head has visited 642 cells. The C simulator agrees with the Python reference simulator on the first 80 records of the run (a test).

tools/c/tmrun.c, tests/test_machine.py

No simple conserved quantity

No a·ones + b·pos + W[state] is conserved modulo 2 to 12, so a linear invariant like the first holdout's mod-3 count does not exist here.

tools/py/bbtools/invariants.py

No pass meets a gap of 3, and runs stay even

In the first 1010 steps there are 344,806,676 pass starts. At each one c/passes.c reads the cells ahead and finds the gap that will end the pass: never a gap of 3. And every run of 0s or 1s of length 3 or more between cells of the other symbol (away from the head) has even length: no odd run at any pass start. A Python version also runs each pass and checks the prediction against the machine (no mismatch in 106 steps).

c/passes.c, py/passes.py check, tests/test_passes.py

The run follows the macro machine

Run side by side with the machine, the macro machine predicts every one of the 344,806,676 pass starts in the first 1010 steps, cell for cell over the whole tape, and never gets stuck. Python agrees with C, and with the machine on all small configurations.

c/macro.c, py/macro.py check, tests/test_macro.py

heuristic Evidence only

The tape grows very slowly

The visited width is 199 cells after 106 steps and 642 after 1010, so the time per new cell grows fast, far faster than for the other machines studied here. The left part of the tape holds blocks of 1s of even length separated by single 0s; the head reaches new cells on both sides.

py/blank.py records, notes/LAB_NOTES.md

Pass endings look like a binary counter

Almost every pass ends at a gap of length 4j + 2, and each j is about half as common as j − 1. In macro terms half of all passes are B passes, which end at their own head gap h = m + 2, where m is the last segment the F pass before crossed; h = 2, 4, 6, 8, … occur with frequencies halving exactly. In the macro machine the first nonzero gap is counted down by 2 per round and a segment just before it becomes a gap of its own size: a counter whose digits are the gaps. Not a proved description of the run.

py/macro.py stats, notes/LAB_NOTES.md

Only a few odd numbers

If every number in a macro configuration is even, every rule gives even numbers again and none can get stuck. Odd numbers enter only at the left end (popping the empty stack gives a segment 1) and at the last segment. In the run there are at most 4 odd numbers at a time, and F meets two 1s side by side only 546 times in 1010 steps (of 344,806,676 passes).

c/macro.c, notes/LAB_NOTES.md

The macro machine never gets stuck

A description of where the odd numbers can be that the rules preserve and that excludes the two stuck cases. That would prove the machine never halts. An odd number has over a thousand distinct small neighbourhoods in the run, so the description is not tiny; window and pushdown languages over the macro numbers are the next tries.
