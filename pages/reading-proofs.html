The method: read statements, skip proofs

A proof file is a list of named facts. Each fact has a statement (what is claimed) and a proof (instructions that convince the checker). If the file compiles, every proof was accepted. So the proofs are for the machine, and the statements are for you.

/-- A comment for humans. Not checked. -/
theorem sweep_right (n : Nat) (L R : Tape) :
    steps (14 * n) ⟨…⟩ = some ⟨…⟩ := by
  have hn : … := by omega
  exact …

Lean Name in teal. Statement highlighted, between the : and the :=. Everything after := by is the proof, up to the next theorem or def.

(** A comment for humans. Not checked. *)
Lemma oentry : forall a b c,
  fO a (b + 6) (c + 2) -->+ fS1 (a + 1) (b + 6) c.
Proof.
  intros a b c. … lia.
Qed.

Coq Statement between the : and the first full stop. The proof sits between Proof. and Qed. The word Qed means the checker accepted it.

  1. Read the comment at the top of the file. Every generated file opens with a plain-English summary of what it contains and which script wrote it.
  2. Jump to the last theorem. It is the headline: nonhalting : ¬ HaltsFromBlank in Lean, nonhalt : ~ halts tm c0 in Coq. Both say the machine never halts from blank tape.
  3. Check the machine is the right one. Compare the twelve rows of the transition table near the top with the machine's text name. This is the one place a human must look.
  4. Read statements on the way up, as far as you are curious. Lines starting with def or Definition introduce vocabulary. Lines starting with theorem, Lemma or Theorem are facts.
  5. Look at how much was assumed. One command lists every unproved assumption behind a theorem. The section What to trust shows how to read its answer.

Tape notation, and a decoder

In comments and on the explainer pages, a tape is written the usual bbchallenge way: 0^inf B> 0 0 (01)^a 0 0 0 1 0^inf. The head is in state B and is reading the cell just right of B>. (01)^a is the word 01 repeated a times. 0^inf is blank tape to the edge.

In the proof files the same tape is spelled out as data, which is harder on the eye. Three things to know:

  • A cell is false / true in Lean and S0 / S1 in Coq, for 0 and 1.
  • A configuration is three parts: left of the head, right of the head (starting with the cell being read), and the state.
  • The left part is listed nearest cell first, so it reads backwards compared with the tape. The decoder below turns it the right way round.

Counts such as ⟨7, [0, 3]⟩ or mkLin 7 [0; 3] mean 7 + 0·(first variable) + 3·(second variable). With variables k and j that is 3j + 7.

What to trust, and how much

Every claim on a proof-status page carries one of five tags. They say what stands behind the claim.

TagWhat checked itHow it looks in a fileWhat you are trusting
kernelThe proof assistant's kernel, a small program whose only job is to recheck every step.Lean ordinary proofs, rfl, omega, decide +kernel
Coq everything in busycoq/, including vm_compute		The kernel, and that the statement says what you think it says.
nativeLean compiled the check to machine code and ran it. Much faster, used when the kernel runs out of memory.Lean native_decideThe above, plus Lean's compiler. Still far stronger than our own code.
trustedA C or Python program in the repository, run exhaustively. No proof assistant involved.Files under c/ and py/That our program has no bug.
heuristicSampling, curve fitting, a pattern seen in a long run.Prose in the README and status page onlyNothing firm. It is a lead, not a result.
openNobody knows yet.

The three computing words

WordSystemMeaningTag
decide +kernelLeanThe statement is a yes/no question a program can answer. The kernel runs that program itself, step by step, and sees the answer is yes.kernel
native_decideLeanSame question, but the program is compiled and run at full speed outside the kernel. The kernel accepts the answer on the compiler's word.native
vm_computeCoqCoq's fast evaluator. It is part of Coq's kernel, so it counts like decide +kernel, yet it is fast enough for the long runs. This is why the Coq versions need nothing at the native level.kernel

Reading the list of assumptions

Lean's #print axioms nonhalting and Coq's Print Assumptions nonhalt list everything a theorem rests on that was not proved. This is the single most useful line of output.

What still needs a human

  • The transition table. If a row were mistyped, the proof would be about a different machine. Twelve entries to compare. The Lean table is generated from the text name by leangen.py, but checking it by eye takes a minute.
  • The meaning of "step" and "halts". In Lean these are our own definitions, about thirty lines in tools/lean/TM/Basic.lean. In Coq they are busycoq's, written by someone else for the bbchallenge BB(5) effort. A proof against definitions we did not write is the stronger evidence, which is why the Coq versions exist.
  • Comments are not checked. A comment can drift from the statement under it. When they disagree, the statement is what was proved. The decoder above lets you compare a template with its comment.

What you do not need to trust: the Python generators, the tables of numbers they write, or the symbolic checker auto. A wrong number makes a check return false and the build fail. The checker comes with a soundness theorem (auto_reach in Lean, auto_sound and rules_sound in Coq) proving that an answer of true means the real machine makes that run.

Three words to search for. sorry, Admitted and axiom. Each marks something assumed without proof. A search on 12 November 2026 of both machines' Lean folders and all of busycoq/ found none.

Step counts. Lean statements give exact step counts: steps (14 * n) c = some c' means exactly 14n steps. Coq statements only say "reaches": -->+ is one or more steps, -->* is zero or more. In Lean, a machine that halts on its next step has step c = none; bbchallenge counts that halting move as one more step.
