# Lab notes: 1RB0LF_1RC0LB_1RD1RB_1RE1RF_1LA---_0RC1LA

## 2 November 2026: setup and first look

Set up on the shared tools (`../../tools`): `lean/Machine.lean` generated by `bbtools.leangen` (namespace `BB6e`),
bounded runs in `lean/Blank.lean`, the reference simulator wrapped in `py/blank.py`, both pages built from
`status.json`.

The table, with the halting transition E1:

| state | on 0 | on 1 |
|---|---|---|
| A | 1RB | 0LF |
| B | 1RC | 0LB |
| C | 1RD | 1RB |
| D | 1RE | 1RF |
| E | 1LA | halt |
| F | 0RC | 1LA |

**Where a halt comes from.** E is entered only by D0 (write 1, move right), and D only by C0 (write 1, move
right). So the machine halts exactly when D reads a 0 whose right neighbour is 1 (`halt_shape`, kernel). B sweeps
left over 1s erasing them (B1 = 0LB).

**Bounded runs.** No halt in 20,000 steps (kernel), 10⁷ (`native_decide`), 10¹⁰ (C `tmrun`: 313 ones, 642 cells
visited; the last new cell before that was reached at step 9,311,800,524, on the left).

**No linear invariant.** `bbtools.invariants` finds no conserved a·ones + b·pos + W[state] modulo 2 to 12.

**No small closed tape language.** `bbtools.ctl` with windows of K = 3 to 6 cells closes, but every one of them still
allows a halt (`E` on a 1 with `1 1 0 …` to the left), so window CTLs of this size do not decide the machine.

**D reading a 0.** In the first 3·10⁶ steps D reads a 0 103,296 times, always with a 0 to its right (57 of them at
the right end of the visited tape). `python3 py/blank.py dzero STEPS` lists them.

**Growth.** The width is 128 cells after 10⁵ steps, 199 after 10⁶ and 642 after 10¹⁰: much slower than the other
machines here, so the time per new cell grows quickly and a pass over the tape is probably nested inside a counter.
The records (`python3 py/blank.py records 100000 60`) alternate between right-end visits `… 0 1^b B>0` followed by
`C>0`, `D>0`, `E>0` one step apart, and left-end visits `F>0 0 1 0 1 0^2 1 0 1 0 1 …`. At the right ends the tape is
blocks of 1s of even length separated by single 0s.

## 2 November 2026: passes, which of them halt, and a parity invariant

**The mechanism.** The head bounces. Moving right, C and B fill a *sparse* region (single 1s with runs of 0s between
them) into solid 1s: C1 = 1RB, B0 = 1RC, so `C>1 0 1 0 …` becomes `1 1 1 1 … C>`. Moving left, A and F turn a solid
block back into alternating cells: A1 = 0LF, F1 = 1LA, so `1^(2k) A>1` becomes `A>1 (1 0)^k`; B erases 1s
(B1 = 0LB). At every right turn the tape left of the head is solid (blocks of 1s of even length separated by single
0s) and the tape right of it is sparse (single 1s, rarely two, separated by runs of 0s).

**The pass (proved, kernel: `lean/Pass.lean`).** Call a *gap* a maximal run of 0s between two 1s. A pass starts when
the head turns right: F or B, having just moved left, reads a 0, which is the first cell of a gap, and moves right
(`start_F`, `start_B`); C then stands on the gap's second cell. C crosses gaps of length 1 and 2 (`gap1`, `gap2`, and
`pass` for any list of them, by induction). The first gap of any other length ends the pass:

| ending gap | what happens | theorem |
|---|---|---|
| 3 | C0, D0, then E reads a 1: **halt** | `pass_halt` |
| 4 or more | C, D, E write three 1s; E0 turns left, A on the middle one | `pass_turn_E` |
| 0 after a gap of 1 (`1 1`) | B reads the second 1 and erases leftward | `pass_turn_B1` |
| 0 after a gap of 2 | F reads the second 1 and turns left (A) | `pass_turn_B2` |

So **a pass halts exactly when the first gap it meets that is not 1 or 2 has length 3** (`pass_outcome`). Every
rightward run of the machine is a pass (A0 = 1RB also moves right, but only at the end of a sweep, and B turns back
left at once), so the machine halts iff some pass of the run from blank tape meets a gap of 3. The pieces of the
leftward run are proved too: `sweep` (A/F over `1^(2k)`), `sweep_end_odd` (the 0 left of an odd block: F keeps it and
a pass starts), `sweep_end_even` (A fills it and B starts erasing the block before), `erase` (B over `1^k`) and
`erase_end` (B writes a 1 on the 0 it reaches and a pass starts on the erased cells).

**The parity invariant (observed; trusted C up to 10¹⁰ steps).** At every pass start of the run, every run of 0s or of
1s of length 3 or more that has the other symbol on both sides (and does not touch the head) has *even* length. A gap
of 3 is an odd run of 0s, so as long as this holds the machine cannot halt. Where the parity comes from: a pass fills
1 + 2 + … cells and ends at a gap g ≥ 4 by filling 4 of its cells (B or F's cell, then C, D, E), which leaves g − 4,
the same parity; after an even block's sweep, B erases the block before it (even length n) and the two cells after it,
which with the 0 the sweep left beside them is a gap of n + 4 counted from B's cell, and the pass that starts there
fills 4 of it and leaves n; the sweep itself only makes single 0s. An odd block or an odd gap would have to come from one of these steps
seeing an odd length first. `c/passes.c` checks the invariant and predicts the end of every pass from the cells ahead:
in the first 10¹⁰ steps there are 344,806,676 pass starts, none
has a gap of 3 ahead, and none has an odd run anywhere on the tape (width 642 at the end; about 5 minutes). `py/passes.py check` does the same in Python, and also runs each pass to compare the predicted ending
with the machine (no mismatch in 10⁶ steps; `tests/test_passes.py`).

**Pass endings look like a binary counter (heuristic).** Almost every pass ends at a gap of length 4j + 2, and each j
is about half as common as j − 1 (in 10¹⁰ steps: 172,402,771 passes end at 6, 86,201,001 at 10, 43,096,021 at 14,
21,551,100 at 18, 10,779,244 at 22, … 10,370 at 62; the ratio stays 2.00 to three digits). Endings at 0 and at multiples of 4 are rare (about 3,000 of 3.4·10⁸). Consecutive passes tend to end at the same j
while the head drifts right two cells per pass, then j drops. This ruler-like distribution, together with a width that
grows like the logarithm of the time (10⁶ steps: 199 cells, 10¹⁰: 642), suggests a counter whose digits are the gap
lengths; the carry that reaches the end of the tape is what widens it. The exact macro map is not found yet.

**Closed tape languages tried (none decides it).** Window CTLs (`bbtools.ctl`, K = 2 to 6), windows with the length of
the nearest run modulo 2 or 4 (K ≤ 10), and automata that keep the lengths of the J nearest runs up to C plus parity
(C ≤ 4, J ≤ 3), with or without the set of farther run classes: all close but allow a halt. The halts they allow come
from merging tapes that differ far from the head: for example a 1-run of 4 on the sparse side, which the real run never
has. A first try at a language that encodes "solid left, sparse right" directly (the J nearest runs exact, farther
runs on the left 1-runs of even length and single 0s, farther runs on the right single or double 1s and 0-runs of 1
or even length) finds no halt but does not close: with C = 4, J = 3 it needs a run of three 1s on the right, from E
filling the last cell of a gap of 4 next to a `1 1` (which the run never has). Refining that language is the most
direct route to a proof.

**The theorem to aim for.** With `OddGap t` meaning: the stream `t` has a run of exactly three 0s with 1s on both sides,

```lean
/-- F or B on a 0, about to move right: every pass start, and also B crossing a gap of 1 inside a pass (the cells
    ahead are the same as at the pass's start, so nothing is lost by including them). -/
def PassStart (c : Config) : Prop := (c.st = .F ∨ c.st = .B) ∧ c.r 0 = false

/-- Halting is decided at pass starts (provable from `pass_outcome`): the run halts iff some pass start of the run
    has, ahead of it, gaps of 1 and 2 and then a gap of 3. -/
theorem halts_iff_pass_gap3 :
    HaltsFromBlank ↔ ∃ n c gs R, steps n init = some c ∧ PassStart c ∧ (∀ g ∈ gs, g = 1 ∨ g = 2) ∧
      tail c.r = app (word gs) (app [false, false, true] R)

/-- The parity invariant (open): at every pass start, no run of 0s or 1s of odd length ≥ 3 between cells of the
    other symbol.  It implies that no pass meets a gap of 3, so the machine never halts. -/
theorem parity_at_pass_starts : ∀ n c, steps n init = some c → PassStart c → ¬ OddRun c.l ∧ ¬ OddRun (tail c.r)
```

The second is the real question; the first only needs `pass_outcome` and the fact that a halt is the end of the pass
it belongs to.

**Next.** (1) Find the macro map: how a pass ending at gap 4j + 2 changes the solid blocks and the gaps, and whether
the run is a counter. (2) Prove the parity invariant, either by induction on passes with the pass and sweep lemmas
above or with a closed tape language built for it. (3) Prove `halts_iff_pass_gap3`.

## 2 November 2026: the macro machine

**The shape at every pass start (checked: C over 10¹⁰ steps).** Write the tape at a pass start as

    0^∞ 1^(2s₁+2) 0 1^(2s₂+2) 0 … 0 1^(2sₚ+2) [head] 0^(2h+1) 1 (0 1)^m₁ 0^(2n₁+2) 1 (0 1)^m₂ 0^(2n₂+2) 1 … (0 1)^mₜ 0^∞

a *stack* of solid blocks of even length (the top, sₚ, next to the head), a *head gap* of 2h + 2 cells counting the
head's own cell, and a *word* of *segments* (0 1)^m and *gaps* of 2n + 2 cells. A gap with n = −1 is two 1s side by
side; n = 0 is the gap of 2 cells that a pass crosses; n ≥ 1 ends a pass. (Lean and `py/macro.py` count the gap as
g = n + 1, so that it is a natural number.) Every pass start of the run has this shape, F always with h = 0 (`F> 0 0
1`), B with h ≥ 1 or with blank tape ahead, and the states alternate B, F, B, F, …. Below, `B 0 1 | 4 | 2 <0> 6 <-1> 1`
is a configuration in state B with stack 0, 1 (bottom first), head gap h = 4 and word 2 <0> 6 <−1> 1.

**The rules (proved, kernel: `lean/Macro.lean`).** From one pass start to the next:

* **B**, head gap h ≥ 1: pop the top j of the stack (j = −1 if the stack is empty). B fills four cells of its gap and A
  sweeps the block back into a segment: F, head 0, word **(j + 2) <h − 2>** m₁ <n₁> …. With blank tape ahead the word
  is just j + 2.
* **F**: let i be the first gap with nᵢ ≠ 0 (blank tape counts as a gap n ≥ 1), and m₀ = 0. The pass turns every
  segment before it into a block.
  * nᵢ ≥ 1: push 0, m₁, …, m_{i−2}; the block of m_{i−1} is erased and becomes the head gap: B, **h = m_{i−1} + 2**,
    word mᵢ **<nᵢ − 2>** m_{i+1} ….
  * nᵢ = −1 (two 1s side by side), with mᵢ ≥ 1 and m_{i+1} ≥ 1: push 0, m₁, …, m_{i−1}; B, **h = mᵢ**, word
    **(m_{i+1} − 1)** <n_{i+1}> …. If m_{i+1} is the last segment it may be 0, and then the tape ahead of B is blank.

The first pass start, after 12 steps, is `B | 1 | 1` (`B> 0^4 1 0 1`, `blank_to_M0`). In Lean the rules are
`BB6e.mstep`, and `mstep_sound` proves that the machine goes from each configuration to the next for every value of
the parameters (pieces: `unit_cross`, `end_big`, `end_double`, `b_pass`, built from the lemmas of `Pass.lean`). The
rules do not apply in exactly two cases: nᵢ = −1 with mᵢ = 0, and nᵢ = −1 with m_{i+1} = 0 before another gap. The
second would turn the following gap into one of odd length, which is where a gap of 3 and a halt could come from. So
(`no_halt_of_macro`, kernel):

> if the macro machine never gets stuck from `B | 1 | 1`, the machine never halts from blank tape.

The question is now about lists of numbers, with no tape left in it.

**Checks.** `c/macro.c` runs the machine and the macro machine side by side and compares the whole tape at every pass
start: 344,806,676 pass starts in 10¹⁰ steps, no mismatch, no stuck configuration. `py/macro.py check` does the same
in Python; `tests/test_macro.py` also checks `mstep` against the machine on every small configuration (about 22,000)
and C against Python.

**The even sea (proved by inspection of the rules; not in Lean yet).** If every number in a configuration is even, F
never meets n = −1 (gaps go down by 2 from an even value, reach 0 and are crossed), and every rule gives even numbers
again. Odd numbers enter at two places only: popping the empty stack (j = −1 gives a segment 1, at the left end of the
tape) and the last segment. An odd segment becomes an odd gap (as m_{i−1} + 2 and then h − 2), an odd gap counts down
to −1, and only a gap at −1 can get the machine stuck. So everything that could make it halt is carried by a few odd
numbers in a sea of even ones.

**What the run does (C, 10¹⁰ steps).** Of 344,806,676 pass starts, 172,403,331 are B passes, 172,402,792 are F passes
that end at a gap n ≥ 1, 7 are B passes with blank tape ahead, and only 546 F passes meet two 1s side by side
(65 by 10⁶ steps, 124 by 10⁷, 214 by 10⁸, 298 by 10⁹, 546 by 10¹⁰). No pass start in 10¹⁰ steps has had more than 4 odd numbers in its configuration (counting stack, head gap, segments and gaps n). Those
are the passes that ended at a gap of 0 or a multiple of 4 in the earlier tally: a pass ends at a gap of 2n + 2 cells,
so odd n is a multiple of 4.

**The "binary counter" (heuristic).** The halving of pass endings is the distribution of the head gap of B, h = m + 2
for the segment m that F crossed last: in 10⁶ macro steps h = 2, 4, 6, 8, 10, 12 occur 250,030, 125,189, 61,984,
31,360, 15,687 and 7,792 times. In the even sea, two macro steps from F to F are

    F | 0 | … m_{i−2} <0> m_{i−1} <0> mᵢ <nᵢ> …   →   F | 0 | … (m_{i−2} + 2) <m_{i−1}> mᵢ <nᵢ − 2> …   (i ≥ 3)

(with m₁, …, m_{i−3} and a 0 pushed), and for i = 1 the stack's top t comes back as a segment: `F | 0 | (t + 2) <0>
m₁ <n₁ − 2> …`. The first nonzero gap is counted down by 2 per round, and a segment that ends up just before the
stopping gap becomes a gap of its own size: a counter whose digits are the gaps, with the stack as its carry. This is
not a proved description of the run.

**Next.** A closed description of where the odd numbers can be. In 5·10⁵ macro steps an odd number has 1,152 distinct
neighbourhoods (two neighbours on each side, values above 5 kept only by parity), so it is not small at that
resolution, but the macro machine is a much smaller object than the tape: a window language over its numbers (values
capped, kept by parity), or a pushdown abstraction with the stack exact, are the natural next tries.

## 2 November 2026: closed tape languages that do not close

These are attempts at a proof of non-halting by a closed set of configurations that the computer finds. None of
them closed. They are recorded so that the next attempt starts past them.

**Run windows on the tape (Python, scratch).** Write each side of the head as runs of 0s and 1s, with lengths exact
up to C and by parity above. Take the abstract state to be the k nearest runs on each side, and the far language to
be the (k+1)-run windows seen in the real run. The real window set saturates early: 191 windows at C = 4, k = 5, the
same after 10⁷, 10⁸ and 10⁹ steps. The machine run on the abstraction, however, keeps producing windows the real run
never shows:

| C | k | windows | new windows (fails) |
|---|---|---|---|
| 4 | 5 | 191 | 304 |
| 4 | 6 | 311 | 499 |
| 4 | 7 | 405 | 1,471 |
| 6 | 6 | 697 | 1,323 |
| 8 | 6 | 1,125 | 3,375 |

The fails cluster around a gap of 4 at the end of a pass followed by `1 0 1 0^2j` or `1 1`. The count does not shrink
as k grows, so the invariant is not local on the tape. Learned-gram variants (the far language grown until closed)
always reached a halt.

**A pushdown reduction (trusted Python and C: `py/pds.py`, `c/pds.c`, `tests/test_pds.py`).** One side of the tape is
abstracted by a DFA, read from the far blank end toward the head with δ(0, 0) = 0. The other side is kept exactly, as
the stack of a pushdown system whose control states are (DFA state, machine state):

* a move toward the exact side pushes the written cell into the DFA and pops the stack;
* a move toward the DFA side pops the DFA nondeterministically (every (q′, x) with δ(q′, x) = q) and pushes two cells.

Pushdown reachability is regular. Post* saturation (Schwoon) computes exactly which abstract configurations are
reachable from blank tape, so for a given DFA the only loss is the DFA itself. On 600 random 2- and 3-state machines
the decider never proves a halting machine non-halting, and C agrees with Python on random 6-state machines.

For this machine, **no DFA with at most 7 states works, on either side** (every canonical DFA: 1, 4, 45, 816, 20,225 and
632,700 of them for 1 to 6 states, 23,836,540 for 7). The DFAs built by hand fail too:

* run length mod 2, 4 or 8 with zero runs capped;
* the same with a sink for an odd block closed by a 0;
* exact run lengths up to 8 and then by parity.

The shortest abstract halting path for the mod-4 DFA explains why. Popping the left side forgets exact short run
lengths at the left edge of the tape: a run of 1 looks like a run of 5. B then erases a longer block than the tape
has, which makes a long gap of the wrong length.

**A pushdown on the macro machine (Python, scratch).** I tried the same idea on the configurations of
`lean/Macro.lean`, with values exact up to K and by parity above.

* *Word exact, stack S kept as its top k values:* gets stuck for K ≤ 2 and k ≤ 2. Popping S yields arbitrary odd
  values, so odd numbers multiply.
* *Stack exact, word abstracted as runs of all-even tokens around a few exact "defect" tokens:* bounded search finds a
  spurious stuck path. The first spurious step pops an even token with a gap n ≥ 2 where the real token has n = 0,
  which ends a pass the real machine continues.

The tokens that are not (m even, n = 0) are not few. Their number grows with the run (up to 18 in 10⁶ macro steps,
typically 9 to 13), so no abstraction that keeps a bounded number of them exactly can close. Whatever describes the
odd numbers has to describe the counter's digits too.

**Defect census (Python, scratch).** I mapped each macro configuration to a skeleton:

* a token (m, n) with m ≥ 2 even and n even becomes ".";
* every other token is kept as m ∈ {0, odd, even} and n ∈ {−1, odd, even};
* stack values are kept by parity;
* runs of "." collapse to "*".

The number of distinct skeletons is 530, 682 and 701 after 10⁵, 10⁶ and 3·10⁶ macro steps, so it saturates. Since the
"*" runs carry the counter, this is evidence for a regular description, not a description.

## 2 November 2026: first tries at a closed family for the macro machine

**Stuck configurations exist near the run's own shapes (checked by `py/macro.py`).** `F 0 | 0 | 3 <0> 1 <1> 1` (stack
0; word 3 <0> 1 <1> 1) gets stuck after 11 macro steps: it reaches `F 0 1 | 0 | 4 <0> 0 <−1> 1`, a gap n = −1 with an
empty segment on its left. Every value in it is small and it has only three odd numbers, so a closed family has to say
how the odd numbers sit relative to each other, not just how many there are.

**Skeleton languages (abstract search, not closed).** A sibling thread found that, writing a word pair (m, n) with m ≥ 2
even and n even as `.`, collapsing runs of `.` and of even stack values, and keeping everything else by value class, the
run shows only about 700 distinct skeletons up to 3·10⁶ macro steps. Taken as a language and closed under an abstract
`mstep` (values exact up to C, then by parity; each collapsed run expanded to length 1), it does not stay safe: with
C = 2 the closure reaches a stuck configuration after about 13,000 skeletons, with C = 4 after about 540,000 (the path
ends in the example above). So the parity skeleton plus small exact values is not an invariant. The next attempt should
keep a relation between an odd gap and the segment to its right (in the run, the segment right of a gap at −1 is even
and at least 2 in almost every case), or track the odd numbers as particles with explicit rules.

**Window languages on macro tokens (random closure test, not closed).** Windows of K consecutive macro tokens (values
exact up to C, then parity) seen in the run, closed by sampling: K = 3, C = 4 reaches stuck configurations; K = 5, C = 6
keeps adding windows after 30 rounds (74,000 windows, no stuck configuration sampled).
